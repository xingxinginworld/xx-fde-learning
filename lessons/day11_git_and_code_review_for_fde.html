🎯 一、今日目标

导师说

你在某公司多年，Git 大概率是"用过"但没系统学过——clone 会、commit 会、push 会，一遇到冲突就叫开发。这种程度做 PM 够用，做 FDE 不够。FDE 每天要读开发提交的 diff、要自己去改 Prompt 和配置、要给开发提有质量的 issue。你不用当开发，但你得能自己动小手术。

今天要教你的不是 Git 全部命令，是 FDE 场景下最常用的 20 条；不是全栈 code review，是 看 Prompt / 配置 / Agent 逻辑这几块的 review 视角。学完你能自己改 Prompt 提 PR 不叫开发，能提出的 issue 让开发一看就懂——这两件事就把你和普通 PM 拉开一个身位。

  • 掌握 「20 条 Git 命令」，按日常/协作/救火三档分类背熟
  • 会用 「FDE 5 个 Code Review 关注点」 看一段 Agent 代码找问题
  • 能写 「让开发不火大的 Issue」——含复现步骤 / 期望 / 环境 / 建议
  • 敢开 branch 提 commit 推 PR——分支就是保险，不怕搞坏主干
  • 能对开发说出 「我看你这段 Prompt 硬编码了，建议抽到 config」 的话术

📖 二、核心讲解

是什么：FDE 要读的代码到底是什么

先破个误会——FDE 不是要读全部代码。开发写的业务 CRUD、UI 组件、数据库连接池这些你可以不管。FDE 需要读的是这四块：

代码类型在项目里长啥样你要能干什么
① Prompt / 提示词prompts/*.txt、*.py 里的 f-string、YAML 配置看懂、能改、能提 A/B 版本
② Config / 参数配置config.yaml、.env、settings.py知道每个参数干啥、敢改敢回滚
③ 数据管道ETL / 切片 / 向量化 / 数据清洗脚本看懂流程、知道 chunk_size 之类关键参数在哪
④ Agent 逻辑工具定义 / 意图路由 / 多步编排看懂 flow、能画时序图讲清楚

反直觉的地方：这四块加起来通常只占项目代码 10-20%，但它们决定了 80% 的效果。这才是 FDE 最应该盯紧的地方。

□ □ □ Git 日常五连击 □ □ □
clone · branch · commit · pull · merge
拉代码 → 开分支 → 提改动 → 拉更新 → 合并 · 90% 的日常操作在这里

为什么：FDE 读代码的三个大坑

🚨 坑 1 · 觉得"读代码是开发的事"

"我是 PM 不是开发，代码让开发写让开发看"——这句话在传统交付里能过，在 FDE 岗位上是死刑。你不读代码，就永远只能等开发回复——客户催一个 Prompt 微调，开发排期两周后，你没法自己上手。

更糟的是——开发写完你不 review，Prompt 里硬编码了客户名、参数不可配置、日志一行没有，等到部署到客户环境炸了，客户找你，你回去找开发，开发说"这周没空"，然后循环——这就是外包 PM 转 FDE 最容易翻船的地方。

🚨 坑 2 · 只会 clone 不敢 branch commit

Git 的核心哲学一句话：分支就是保险。你在自己的分支上想改啥改啥，改坏了删掉重开一个就完事，主干（main/master）永远干净。

可很多 PM 学 Git 只学到 clone，然后直接在 main 上改，改坏了 git reset --hard 又不敢，最后叫开发帮忙——这就是不敢 branch 的代价。

正确姿势：拿到任何仓库第一件事——git checkout -b feature/xxx-fix，从此在自己的分支上折腾，天塌了就 git branch -D 删掉重来。

🚨 坑 3 · 提 issue 只说"跑不了"

你以前当 PM 转达客户问题，习惯性一句"客户说这个功能有问题"就丢给开发。开发看到就火大——什么问题？怎么复现？期望是什么？在哪个环境？ 一问三不知，来回三轮才定位到问题。

FDE 提 issue 有标准模板（下面速查卡有），最少 5 个字段：Title / Steps to reproduce / Expected vs Actual / Environment / Suggestion。开发一看就能动手，不用来回追问。

老 PM 的通病：你觉得"我把客户的话原话转给开发就完事了"——不是。FDE 的价值就是做一层信息压缩和结构化，让开发不用再花时间猜。

🧭 PM 行动指南：FDE Code Review 5 个关注点

① Prompt 有没有硬编码——客户名、模型名、系统提示词是否可配置？换个客户要不要改代码？

② 参数是否可配置——chunk_size、top_k、temperature、max_tokens 是不是都在 config 里？不在的话调优就要改代码。

③ 错误处理是否完备——LLM API 超时、限流、返回格式异常、工具调用失败——每一种都有兜底吗？

④ 日志是否够——input / prompt / output / usage / latency 有没有埋？出问题能不能靠日志定位？

⑤ 是否有测试——评测集在哪？回归测试怎么跑？有没有 fixture？

怎么用：Code Review 4 步法

1
先跑一遍——review 之前先把代码 clone 下来能跑通。跑不通说明 README 有问题、依赖有问题，这本身就是一条 review 意见。能跑起来才敢评论。
2
读整体结构——先看目录树和入口文件，画一个模块关系图。理解 数据从哪进来、经过哪几个模块、从哪儿输出。别一上来陷进某个函数细节。
3
按 5 个关注点找问题——对着上面那 5 条清单一条条扫。找硬编码 grep 一下 "客户名"；找参数配置看 config.yaml；找错误处理搜 try/except；找日志搜 logger；找测试看 tests/ 目录。5 分钟能出 5 条意见。
4
提问题不提断言——review 评论用问句比断言好："这里为啥没做超时兜底？"比"这里必须加超时"好——你不是老板是同行者。给建议要给 怎么改的思路 / 参考，不是光丢一句"这里不对"。

导师说

下面这段 30 行代码是我给某电力公司做知识问答 Agent 时，开发第一版提交上来的代码。你先自己看 3 分钟，试着找出问题；然后对照参考答案。这个案例里至少有 5 个可 review 的点。

📌 案例 A · 电力知识问答 Agent 代码（跟着做）
开发提交的第一版代码
# file: qa_agent.py import openai def answer_question(question): openai.api_key = "sk-abc123xxx" # ← 观察 1 prompt = f"""你是某单位某分公司的智能问答助手。 请根据知识库回答用户问题。 用户问题: {question} 请用简洁准确的中文回答。""" # ← 观察 2 # 检索 chunks = vector_db.search(question, top_k=3) # ← 观察 3 context = "\n".join([c["text"] for c in chunks]) response = openai.ChatCompletion.create( model="gpt-4", messages=[ {"role": "system", "content": prompt}, {"role": "user", "content": context + "\n\n" + question} ], temperature=0.7 ) # ← 观察 4 return response["choices"][0]["message"]["content"] # ← 观察 5
Step 1 · 先跑一遍

你 clone 下来跑不起来——为啥？openai.api_key 是硬编码的假 key，且 vector_db 没导入。这本身就是第一条 review 意见：项目没法开箱运行。

Step 2 · 读整体结构

流程还算清楚：接受问题 → 检索 → 生成 → 返回。但没有分文件 / 没有类封装 / 没有配置层——这是"能跑就行"的原型代码，不是生产代码。

Step 3 · 按 5 个关注点找问题
编号对应关注点问题
观察 1① Prompt 硬编码 + 敏感信息API Key 硬编码在代码里，且要 push 到 Git——这是 P0 事故。应改用环境变量 os.getenv("OPENAI_API_KEY")。
观察 2① Prompt 硬编码"某单位某分公司"写死在 Prompt 里，换客户就要改代码。应抽到 prompts/qa_system.txt，客户名走 {customer_name} 变量。
观察 3② 参数不可配置top_k=3 是魔法数字，调优时找不到。应放 config.yaml 里。
观察 4③ 错误处理缺失 + ④ 日志缺失没有 try/except——API 超时、限流、余额不足全会抛异常直接崩。没有任何 logger 记录 input/output/latency——出问题查不到。model="gpt-4" 也硬编码。
观察 5③ 无格式兜底直接下标访问 ["choices"][0]——如果 API 返回结构变了或者 error，直接 KeyError。应先判空判 error。
Step 4 · 写 Review 评论（示范）

@开发同学，整体流程清晰，但有几个我担心的点想跟你讨论下：

1. [P0] API Key 硬编码——第 4 行 openai.api_key 直接写在代码里，如果 push 到 Git 上 key 就泄漏了。是不是应该改成 os.getenv("OPENAI_API_KEY")，并把 .env 加进 .gitignore？

2. [P1] 客户名硬编码——"某单位某分公司"写在 Prompt 里，我们后面要接别的客户就得改代码。能不能抽到 prompts/qa_system.txt，客户名用 {customer_name} 参数注入？

3. [P1] 无异常处理——OpenAI API 会遇到 429 / 500 / 超时，现在这段代码只要出一次就整个 Agent 崩掉。建议包一层 try/except + 重试装饰器（tenacity 库可以直接用）。

4. [P2] 无日志埋点——现在这段代码出问题只能靠猜。参考 Day 10 讲的可观测性，最低要记 input/prompt/output/usage/latency。

5. [P2] 魔法数字——top_k=3、temperature=0.7、model="gpt-4"都建议进 config.yaml，我们后面调优不用改代码。

整体没啥大问题，属于第一版原型阶段该有的样子。上面 5 条改完就能进 PoC 了。辛苦。

📓 复盘一句话

Review 不是挑刺，是同步担心。措辞用问句 + 分优先级 P0/P1/P2，开发接受度高 10 倍。

🧪 案例 B · RAG 切片代码 review（自己练）

假设你看到下面这段 RAG 切片代码，请你按 5 个关注点找出问题：

def build_rag_index(): docs = load_all_pdfs("/data/customer_docs/") chunks = [] for doc in docs: text = doc.extract_text() for i in range(0, len(text), 500): chunks.append(text[i:i+500]) embeddings = openai.Embedding.create( model="text-embedding-ada-002", input=chunks ) milvus.insert("kb_index", embeddings) print("done")
查看参考答案

至少 6 个可 review 的点：

  1. 路径硬编码 /data/customer_docs/——应传参 / 走 config
  2. chunk_size = 500 硬编码——500 字符是不是太小/太大？应放 config，方便调优
  3. 切片策略太粗——按固定字符切会切断句子和上下文，应用 RecursiveCharacterTextSplitter 加 chunk_overlap
  4. 无异常处理——某个 PDF 提取失败会中断整个流程，应 try/except 单个文档 + 记录失败清单
  5. 用 print 代替 logger——生产代码不能用 print，应用 logging 记录：多少文档、多少 chunk、耗时
  6. 无索引版本管理——每次重建都覆盖 kb_index，出问题回不去。应加版本号 kb_index_v20240315，切换用别名

加分项：问一句"这个 embedding 模型是 OpenAI 的，客户内网出不去，怎么办？"——这个问题涉及 Day 12-13 的白名单问题，本身就是好 review。

🧪 案例 C · 判断题：反例 vs 正例 issue（自己练）

反例 Issue：

标题：跑不起来

内容：客户那边说 Agent 有问题，你看下什么情况。

正例 Issue：

标题：[Bug] RAG 查询"招标截止时间"返回"投标截止时间"，疑似检索层召回错误

Steps to reproduce:

1. 在客户环境（青海分公司生产环境 v0.3.2）打开 Agent

2. 输入问题："2024 年智能配电终端项目招标截止时间是什么时候？"

3. Agent 返回："投标截止时间是 2024 年 3 月 15 日"

Expected: 返回招标文件领取截止或说明该字段无法查询

Actual: 返回了投标截止时间，语义错误

Environment: v0.3.2 / 青海生产环境 / qwen-max / 2024-03-10 14:22:11

Trace ID: trace-abc123（Langfuse 链接）

Suggestion: 疑似检索层"招标"vs"投标"语义混淆，见 Trace 中 top-3 均为"投标"chunk。建议加 BM25 + 向量混合检索。

对比两个 issue，说说好 issue 有哪 5 个要素。

查看参考答案

好 issue 的 5 个要素（BUG 类）：

  1. Title：一句话说清"什么场景 + 什么问题 + 疑似原因"——开发扫标题就能判断优先级
  2. Steps to reproduce：能复现——最少 3 步，别人拿到能一步步跟着操作
  3. Expected vs Actual：预期是什么、实际是什么——差异明确，避免"我以为的 vs 你以为的"
  4. Environment：版本 / 环境 / 时间戳 / Trace ID——开发能快速定位到对应日志
  5. Suggestion：给个思路（可选但强推荐）——你不用给完整方案，但给方向让开发少走弯路

反例的错法："跑不起来"是最糟的 issue——没复现、没环境、没证据、没建议。开发第一反应是"你能不能自己先查一下再来？"

老 PM 转 FDE 最容易犯的错：习惯性把客户原话直接甩给开发。FDE 的价值就是 在客户原话和开发行动之间做一层压缩和结构化——issue 质量就是这层压缩的产物。

📝 五、5 题小测验

建议先自己想 20 秒再点开答案。错项解析比正确答案更值钱。

Q1 · 拿到一个新仓库要改一段 Prompt，第一步最正确的是？
  • A. 直接在 main 分支上改，改完 commit push
  • B. 先 fork 一份自己的仓库再改
  • C. git checkout -b fix/prompt-xxx 新开分支再改
  • D. 找开发同学帮改，自己不动手
✅ 答案：C

分支就是保险——新开分支改，改坏了删掉重来主干干净。这是 Git 最基本的纪律。

❌ 错项解析

A 是最典型的新手错法——直接改 main，改坏了 push 上去全组遭殃。B fork 是外部贡献者玩法——同一个团队内 fork 反而复杂化，多数场景开分支就够。D 是最坏答案——FDE 岗位就要求你能自己改小改动，永远等开发就是永远做不了 FDE。

Q2 · Code Review 里发现开发把 API Key 硬编码进了代码，正确处理是？
  • A. 私下告诉开发让他改，别公开评论怕他没面子
  • B. 在 review 里标 [P0]，说明理由并给出替换方案（环境变量）
  • C. 自己在合并前偷偷把 key 改成假的
  • D. 无所谓反正是开发环境的 key，先上线再说
✅ 答案：B

公开标 [P0] 不是让开发难堪，是沉淀团队规范——所有人以后都知道这类问题的严重性。同时给出替换方案是 FDE 的基本礼貌。

❌ 错项解析

A "怕他没面子"这个想法本身就错了——review 是对事不对人的团队机制，私聊反而让规范无法沉淀。C 偷改是最糟的做法——你没告诉开发他就学不会。D 是灾难思维——开发环境的 key 一样值钱，push 到 Git 后爬虫几分钟就能扫到。

Q3 · 下面 5 个关注点里，FDE 最应该盯紧的是？
  • A. Prompt 是否硬编码 + 参数是否可配置 + 错误处理 + 日志 + 测试
  • B. 代码风格是否符合 PEP 8 + 变量命名是否规范
  • C. 数据库连接池大小 + 前端 UI 组件设计
  • D. 单元测试覆盖率是否达到 80% 以上
✅ 答案：A

这 5 条就是 FDE 视角 Code Review 的核心——它们决定了 系统能不能改动、能不能查问题、能不能换客户。B/C/D 是开发或测试角色该管的事，FDE 关注度低。

❌ 错项解析

B 变量命名规范由 linter 自动管，FDE 花时间挑这个是本末倒置。C 是全栈开发或架构师视角，跟 AI 效果关系不大。D 是测试工程师视角，AI 项目单元测试覆盖率不是核心指标，评测集覆盖率才是。

Q4 · 提 issue 时，下面哪个是必填字段？
  • A. 你个人的邮箱和电话，方便开发联系你
  • B. Steps to reproduce + Expected vs Actual + Environment
  • C. 客户领导的姓名和职位，说明这个 issue 有多重要
  • D. 你猜测的完整技术方案，让开发照着做
✅ 答案：B

复现步骤 + 预期实际 + 环境信息，这是"让开发能立刻上手"的最小信息集。开发拿到就能定位问题，不用来回追问。

❌ 错项解析

A 联系方式在项目群里就有，不用重复——issue 是给团队看的技术记录。C 说客户压力是老 PM 的坏习惯——issue 里搞压迫不解决技术问题，反而让开发反感。D 假装是开发是最尴尬的越界——你可以在 Suggestion 里给方向，但完整方案让开发决定。

Q5 · 综合题：领导让你给一个新接手的 Agent 项目做 30 分钟 review，你怎么规划？

给出你的时间分配和 review 计划。

✅ 参考答案：跑通 → 看结构 → 扫 5 点 → 写评论

0-5 分钟 · 跑通：clone 下来按 README 装依赖跑起来。跑不起来记一条"入门体验差"issue。

5-10 分钟 · 看结构：看目录树 + 入口文件 + main 函数。画一个数据流图：input → 什么模块 → 什么模块 → output。理清主链路。

10-25 分钟 · 扫 5 点：

  • grep 客户名/模型名/API URL——找硬编码
  • 找 config 文件——看关键参数是不是都进 config 了
  • 搜 try/except 和 retry——看错误处理覆盖度
  • 搜 logger / logging——看日志埋点
  • 看 tests/ 目录——有没有评测集和回归脚本

25-30 分钟 · 写评论：整理成结构化 review 意见，标 P0/P1/P2 优先级，每一条给出理由 + 建议改法。整体 3-5 条建议，别 20 条把开发压垮。

面试金句："Code review 30 分钟能出 5 条 P0/P1 意见，说明这个 review 有价值。出 20 条鸡毛蒜皮意见，开发看到就想关掉。抓大放小、分优先级，是 review 的核心手艺。"

💼 六、面试金句预埋

可改性意识 "我看代码有一个核心视角——可改性。硬编码越多、参数越死、日志越少的代码，未来越难迭代。Prompt / config / 错误处理 / 日志 / 测试这 5 条是我 review 每个 Agent 项目必扫的关注点。抓这 5 条效率比全量 review 高 10 倍。"
协作效率 "我做 FDE 一个坚持——能自己改的小改动绝不叫开发。Prompt 微调、config 参数调、少量脚本修改都自己上，开分支提 PR 让开发 review。开发省下来的时间，可以用来做真正需要工程能力的架构改造。FDE 的价值不是当二传手，是真正减轻开发负担。"
Issue 质量文化 "我提的每一条 issue 都按 Steps / Expected / Environment / Suggestion 结构化写。这不是形式主义——好 issue 让开发 5 分钟就能定位问题；差 issue 让开发花 30 分钟追问。Issue 质量就是团队协作效率的一半，这是我从外包 PM 转 FDE 学到的最值钱的一课。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. FDE 不用读全部代码——只用读 Prompt / config / 数据管道 / Agent 逻辑这 4 块，它们决定 80% 的效果。（抓大放小，别被业务 CRUD 淹没。）

2. 分支就是保险——不敢开分支，是不敢改代码的根本原因。（git checkout -b 是 FDE 的自由通行证。）

3. Issue 是压缩，不是转达——把客户原话直接甩给开发，是老 PM 的老毛病。FDE 要做结构化压缩。（好 issue 是 FDE 的核心产出物之一。）

🎯 老 PM 转 FDE 的思维切换

你以前的角色是"客户 ←→ 开发的中间人"——传话为主。现在 FDE 的角色是"客户信息压缩器 + 开发协作者 + 小改动动手者"——同一个岗位，价值密度差 3 倍。开分支 / commit / 提 PR 这些动作不难，难的是敢动手。第一次改怕搞坏是正常的，改 5 次以后就自然了。
