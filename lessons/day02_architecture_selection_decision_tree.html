🎯 一、今日目标

导师说

Day 1 你学会了判断"该不该做"，今天要跨到下一步——该怎么做。这是 FDE 和普通 PM 最锋利的分水岭：普通 PM 写"我们采用 AI 大模型技术方案"就交差了，FDE 得敢说"这场景应该用 RAG + 工作流，不该用 Agent，因为……"。

你的雷达图里 ② 会翻译 = 2.4，弱点就在这。翻译不是把中文翻成技术黑话，是把客户模糊的"我要 AI"翻成"我要哪一种 AI 架构"。今天这 70 分钟就补这个。

选架构最反直觉的一点：越牛的架构不等于越好。政企场景里，能用工作流搞定的坚决别上 Agent——一个稳定可控的工作流，永远比一个"看起来智能但每次结果都飘"的 Agent 值钱。

  • 能在客户面前说出 「我为什么选 X 不选 Y」 的完整技术论证

📖 二、核心讲解

是什么：四种主流 AI 架构，一句话说清

先别急着背概念——你只要记住一件事：四种架构解决的是"AI 什么时候动脑、动多少脑"的问题。工作流几乎不让 AI 动脑；Multi-Agent 是让好几个 AI 各自动脑还得会开会。中间的复杂度和成本，可以差 10 倍。

架构 一句话定义 复杂度 相对成本 典型示例（政企场景）
工作流
Workflow		 预定义好的固定步骤，AI 只在某几个节点里做局部智能（抽取 / 分类 / 改写） 低 ★ 1 倍 合同关键字段抽取 → 查风险库 → 出审阅报告
RAG
检索增强		 先从知识库检索相关片段，再让 LLM 基于这些片段有依据地生成答案 低-中 ★★ 1.5 倍 员工制度问答、政策文件查询、产品手册助手
Agent
智能体		 模型自主决策"下一步调哪个工具、传什么参数"，可多轮循环直到完成任务 中-高 ★★★★ 3-5 倍 物资评标辅助（查 ERP + 查历史标 + 打分 + 生成建议）
Multi-Agent
多智能体		 多个 Agent 分工协作，各自扮演不同角色，通过消息 / 编排完成一个大任务 高 ★★★★★ 5-10 倍 投标全流程（招标解读 Agent + 方案撰写 Agent + 报价评审 Agent + 合规审查 Agent）

反直觉的地方：你以为"更智能 = 更好"，实际上政企客户 90% 的场景，工作流 + RAG 就打完了。Agent 是给"步骤真的定不下来"的场景准备的，Multi-Agent 更是稀有——一个人搞得定的活别硬拆成三个人开会。

□ □ □ 架构选型口诀 □ □ □
步骤定 → 工作流
找答案 → RAG
要决策 → Agent
要分工 → 多 Agent
四把钥匙对四种锁 · 选错一把整栋楼白装修

为什么：三个把项目搞崩的高频陷阱

🚨 陷阱 1 · 简单场景硬上 Agent（"AI 秀肌肉"型翻车）

客户要一个"智能报销助手"，你觉得工作流不够酷，硬做了个 Agent——让它自主决定"先查预算表还是先查发票 OCR"。结果同一张报销单跑两次给出不同结论，客户一测就发现，直接叫停。

Agent 的核心特征是 「自主决策 = 输出不稳定」。政企场景最怕输出不稳定——审计和合规部一句"上次这么判、这次那么判"你就没法回答。

正确姿势：步骤能定的坚决用工作流。Agent 的自主性只留给"步骤真的没法预先定死"的场景。成本对比：一样一个报销场景，Agent 方案月推理成本是工作流的 5 倍，效果反而更飘。

🚨 陷阱 2 · 复杂场景用工作流硬撑（灵活性透支）

物资评标辅助——涉及 ERP 供应商查询、历史投标数据、评分规则、多轮补充问询。你把它做成 20 个节点的工作流，写死了流程。上线三个月，客户说"这次品类不一样，评标规则也变了"——你发现每加一个品类就要改 5 个节点，一年下来工作流像意大利面。

怎么判断"该升级到 Agent"？看两个信号：① 分支超过 3 层且分支条件在业务上真的多变；② 需求变更每次都要动核心流程逻辑。这两个信号出现，说明工作流的"预定义"假设已经不成立了。

正确姿势：核心决策交给 Agent，工具（查 ERP、查历史标）保持稳定接口。Agent 层做"调用编排"，工具层做"稳定执行"——变化和稳定分层。

🚨 陷阱 3 · 把 RAG 和 Agent 当成对立选项

面试或客户答辩里最容易翻的坑——被问"你为什么选 RAG 不选 Agent"，慌了直接回答"因为 RAG 简单"。错。RAG 是知识来源的解法，Agent 是决策架构的解法，两者根本不在同一维度。一个 Agent 可以内嵌 RAG（Agent 决定"要不要查、查什么"），一个工作流的某个节点也可以用 RAG。

正确的对立关系是：工作流 vs Agent（决策方式对立）、RAG vs 微调 vs 提示工程（知识来源对立）。混用这两组，客户一眼看穿你没搞懂。

正确姿势：回答时分两层——"知识层我们用 RAG，因为知识频繁更新不适合微调；架构层我们用工作流，因为审批步骤确定。" 这才是 FDE 的表达。

🧭 PM 行动指南：选架构前必须先答的 3 个问题

Q1 · 步骤固定吗？——如果 80% 的场景走同一条主流程，工作流足够；分支 > 3 层且难穷举，才考虑 Agent。

Q2 · 需要外部知识吗？——需要引用大量文档 / 政策 / 手册 → RAG；只用模型内置常识 → 不用 RAG。（这个问题独立于架构选型，任何架构都可能挂 RAG）

Q3 · 需要多步决策 & 工具调用吗？——需要"先查 A，看结果再决定查不查 B"这种动态编排 → Agent；一条直线走到底 → 工作流。

三问答完，架构基本就落地了。写在方案首页的架构选型段，本质就是把这 3 个问题的答案写清楚。

怎么用：五步决策树，5 分钟落地一个架构

1
第一问 · 是不是问答类需求？——"我要一个能回答 XX 问题的助手" → 主干走 RAG。如果是"我要一个能干 XX 事情的助手" → 走后续问题。问答 vs 办事，第一刀分开。
2
第二问 · 主流程有没有 SOP？——客户能画出流程图 / 有明文 SOP，答"能" → 工作流打底。答"能画出主干但异常路径多" → 工作流 + 少量 AI 节点。答"每次都不一样" → Agent 候选。
3
第三问 · 需不需要调多个外部系统 / 工具？——不需要 → 工作流 / RAG。需要且工具调用顺序可以预定 → 工作流串联。需要且顺序依赖上一步的结果 → Agent。
4
第四问 · 一个 Agent 装得下吗？——如果 Agent 的 prompt 已经超过 3000 字、要它扮演 3 种以上角色、决策路径超过 8 步 → 拆成 Multi-Agent。否则单 Agent 优先。Multi-Agent 是最后手段，不是默认选项。
5
第五问 · 演化路径想清楚了吗？——政企项目要考虑二期、三期。工作流 → Agent 的升级路径要提前留（把 AI 节点封装成工具）；不要一步跳到 Multi-Agent 再回头砍。方案文档里写清"为什么现在选 X，未来什么条件升级到 Y"。

🛠️ 三、动手步骤：三个政企场景过决策树

导师说

选架构不是 PPT 上写几行字就完了。你要在客户会议上，被业务和 IT 双向盘问的时候，撑得住每一问。下面三个案例都是政企常见的——第一个我带你走完，后两个自己练，练完再对参考答案。

练的时候刻意用 「五问决策树」 记笔记：每一问的答案是什么、依据是什么、有没有反例。这个记录本身就是你未来方案文档架构章节的初稿。

📌 案例 A · 政企合同智能审阅助手（跟着做）
客户原话

"我们法务每天要审 30 份合同，最花时间的是找关键条款——付款条件、违约金、免责范围——然后对比我们公司的合规红线。我要一个 AI 帮法务预审，重点条款和风险点先给圈出来。"

Step 1 · 是问答类吗？

不是。是"办事"——从合同里抽东西、对比、生成报告。排除纯 RAG 主干。

Step 2 · 主流程有 SOP 吗？

有。法务已经有清晰的审阅 SOP：解析合同 → 抽关键条款 → 对比红线库 → 标风险等级 → 出报告。工作流打底候选。

Step 3 · 要不要调多系统？

要——合规红线库（企业内网）+ 历史合同库（可选）。但调用顺序完全可预定，不需要动态决策。工作流串联即可。

Step 4 · 需不需要 RAG？

需要。合规红线库是频繁更新的知识（法务季度更新条款），非常适合挂 RAG。工作流 + RAG 混合。

Step 5 · 演化路径

一期工作流 + RAG 落地；二期若客户要"审阅后自动起草修改建议 → 发邮件给对方"，再考虑把审阅结果输出到一个轻量 Agent 做后续动作编排。

结论 & 架构图（文字版）
✅ 最终架构：工作流 + RAG

[合同上传] → [OCR/解析] → [LLM 抽条款] → [RAG 检索红线库] → [LLM 打风险等级] → [模板化报告输出]

AI 只在"抽条款"和"打风险等级"两个节点里发挥智能，其他都是确定性代码。稳定、可解释、成本低。

对客户话术

"审阅流程本身已经很清晰，我们把它做成工作流；红线库频繁更新，我们挂 RAG 让 AI 每次都读最新版本。不上 Agent，是因为 Agent 输出会飘，法务审阅要求可解释、可复盘。"

客户原话："我们集团制度文件有 200 多份，员工问到差旅、请假、报销、股权激励，HR 天天当搜索引擎用。做一个 AI 助手让员工自己问。"

试着走一遍五问，重点想清楚：为什么不该上 Agent。

查看参考答案

结论：纯 RAG。不上 Agent。

五问走查：

  • Q1 · 问答类吗？—— 100% 是。
  • Q2 · 有 SOP 吗？—— 无所谓，不涉及流程。
  • Q3 · 要调外部系统吗？—— 不需要，就是查制度库。
  • Q4 · 一个 Agent 装得下吗？—— 根本不需要 Agent。
  • Q5 · 演化？—— 若二期要"结合员工个人信息答'我还剩几天年假'"，才加一个查 HR 系统的工具，那时再考虑轻量 Agent。

为什么不上 Agent（关键论证）：Agent 的价值在"动态决策工具调用"，这里根本没有多工具、没有决策分支。硬上 Agent 只会：① 成本上升 3-5 倍；② 有一定概率不去检索直接拿模型内部知识瞎答（幻觉风险陡增）；③ 客户合规团队会问"AI 决策依据是什么"你答不上来。

对客户话术："这个场景我们建议用 RAG 而非 Agent——制度问答需要每一句都有出处可查，RAG 天然带引用；Agent 反而可能不查文档直接编答案。"

🧪 案例 C · 某单位物资评标辅助（自己练 · 难度 ★★★★）

客户原话："评标专家每次评一个大品类要看 40+ 家投标供应商，涉及资质核验、历史业绩查询、报价合理性、技术方案打分。我要一个 AI 助手，能像一个初级评标员一样帮我预打分、找疑点、生成初评报告。"

试着走一遍五问，重点想清楚：什么条件下从 Agent 升级到 Multi-Agent。

查看参考答案

结论：一期用 Agent + RAG；二期视复杂度升级到 Multi-Agent。

五问走查：

  • Q1 · 问答类？—— 不是，是"打分 + 生成报告"，办事型。
  • Q2 · 有 SOP？—— 主干有（资质→业绩→报价→技术），但每个环节的具体检查项和权重按品类变化，SOP 覆盖率约 60%。
  • Q3 · 要调多系统？—— 要。至少 3 个：ERP 供应商库、历史评标数据库、企业信用外部 API。而且顺序有依赖——先看资质通不通过，通过再查业绩；报价合理性要参考历史中标价（前一步的输出决定后一步查什么）。这是典型的 Agent 场景。
  • Q4 · 单 Agent 装得下？—— 一期够。四类检查融在一个 prompt 里，大约 2000-2500 字，还没爆。
  • Q5 · 演化路径？—— 二期如果客户要"每类检查生成独立子报告 + 各角色专家复核意见"，此时单 Agent 的 prompt 会爆到 4000 字以上，就该拆成 Multi-Agent（资质 Agent、业绩 Agent、报价 Agent、技术 Agent + 一个总协调 Agent）。

什么时候必须升级到 Multi-Agent（三个信号）：

  • ① 单 Agent 的 prompt > 3500 字，且再加内容会稀释指令跟随；
  • ② 不同角色需要不同的知识库 / 工具权限（比如资质 Agent 能访问工商数据，报价 Agent 能访问历史标价，权限要隔离）；
  • ③ 有明确的"多轮讨论/交叉复核"业务需求（比如两个 Agent 意见不一致要出仲裁流程）。

反直觉提醒：Multi-Agent 不是"更牛"，是"更复杂、更难调、更贵"。一期能用单 Agent 跑通的，坚决不要一步跳 Multi-Agent——你会花 3 倍时间调 Agent 间的通信协议，业务价值反而没上去。

对客户话术："一期我们用一个统一的评标 Agent + RAG（挂业务规则库和历史标价库）跑通主流程；等您专家提出'不同品类要不同角色分工'的时候，我们升级到 Multi-Agent，这个升级路径我们在方案里给您画出来了。"

📝 五、5 题小测验

先自己想 20 秒再点开。错项解析比正确答案更值钱——每一个错项后面都藏着一次真实的翻车。

Q1 · 「工作流」和「Agent」最本质的区别是什么？
  • A. 工作流用 Python 写，Agent 用大模型写
  • B. 工作流步骤和顺序预先定死，Agent 由模型在运行时决定下一步
  • C. 工作流没有 AI，Agent 才有 AI
  • D. 工作流便宜，Agent 贵
✅ 答案：B

本质是"决策发生的时机"——工作流的决策是开发时做的（写代码时定好流程），Agent 的决策是运行时做的（模型看到中间结果动态决定下一步）。这个本质差异决定了工作流稳定、Agent 灵活但不稳定。

❌ 错项解析

A 错在实现语言维度——两种架构都可能用 Python 加大模型 API 实现，语言不是本质区别。C 错在"工作流没有 AI"——工作流的节点里完全可以包含 AI 调用（比如工作流的第 3 个节点让 LLM 抽字段），只是不由 AI 决策流程走向。D 错在只看到了表象——成本是结果不是本质原因，Agent 贵是因为要多轮循环调用，而多轮循环是"运行时决策"的必然结果，抓不到根源就答不好客户追问。

Q2 · 客户说「我要一个 AI 助手回答员工的政策问题，涉及 300 份内部制度文件」——最合适的主干架构是？
  • A. Multi-Agent（分政策类、报销类、假期类 Agent 各一个）
  • B. Agent（让 Agent 自主决定查哪份文件）
  • C. RAG（把 300 份文件切片索引，检索后 LLM 生成）
  • D. 微调（把 300 份文件微调进模型里）
✅ 答案：C

问答类需求 + 需要引用大量文档 + 需要出处可查 → RAG 是教科书答案。这是决策树 Q1 就能直接落地的场景，不需要走到 Q2 之后。

❌ 错项解析

A 错在过度分工——Multi-Agent 是最后手段，一个 RAG 一次检索就搞定的事情，硬拆成 3 个 Agent 会引入协调复杂度和成本，收益却几乎为零。B 错在把 RAG 和 Agent 混了——查文档这件事根本不需要"决策架构"，Agent 反而可能不去检索直接编答案（幻觉风险）。D 错在最贵最不合适——制度文件季度更新，每次更新都要重新微调；而且 300 份文件微调后无法追溯出处，合规团队不会认可。

Q3 · 「五问决策树」的正确顺序是？
  • A. 有 SOP 吗 → 问答类吗 → 工具调用动态吗 → 单 Agent 装得下吗 → 演化路径
  • B. 问答类吗 → 有 SOP 吗 → 工具调用动态吗 → 单 Agent 装得下吗 → 演化路径
  • C. 工具调用动态吗 → 问答类吗 → 有 SOP 吗 → 单 Agent 装得下吗 → 演化路径
  • D. 问答类吗 → 工具调用动态吗 → 有 SOP 吗 → 演化路径 → 单 Agent 装得下吗
✅ 答案：B

顺序背后有筛选粒度的因果：先切"问答 vs 办事"（Q1 一刀切走一半场景到 RAG） → 再切"有没有 SOP"（Q2 决定工作流还是 Agent 大方向） → 再看"工具调用是否动态"（Q3 决定要不要 Agent） → 再看"单 Agent 装不装得下"（Q4 决定单 Agent 还是 Multi） → 最后写演化（Q5 交代给客户看）。

❌ 错项解析

A 错在把 Q2 提前——"有没有 SOP" 只对办事类需求有意义，纯问答类根本没 SOP 概念，先问这个会走弯路。C 错得更远——工具调用是个偏底层的问题，需求类型都没定就问工具，判断没锚点。D 错在把演化路径提前到"单 Agent 装得下吗"之前——演化路径必须基于"当下选了什么"再谈，Q4 都没答就没得演化。

Q4 · 政企客户对「AI 输出稳定性」要求极高的场景（例如财务、审计、合规），你应该优先避开的架构是？
  • A. 工作流
  • B. RAG
  • C. Agent
  • D. 传统规则引擎
✅ 答案：C

Agent 的核心特征是"运行时自主决策"——同一个输入两次跑可能走不同路径，输出不完全一致。这在需要"可复盘、可解释、审计口径统一"的政企场景是致命弱点。合规部一句"上次这么判、这次那么判"你就说不清。

❌ 错项解析

A 错在方向反了——工作流是稳定性最高的架构（步骤和顺序都写死），正是这类场景的首选。B 错在把 RAG 当决策架构——RAG 只是知识来源，本身不影响决策稳定性，一个跑在工作流里的 RAG 是稳定的。D 错得最离谱——传统规则引擎稳定性 100%（if-else 输入相同结果必然相同），压根不该避开，反倒是这类场景的兜底方案。

Q5 · 综合题——客户说「我要一个招投标全流程助手，从招标公告分析、方案撰写、报价评审到合规审查全都能干」，请给出架构选型和理由。

用五问决策树走一遍，写下你的判断。

✅ 参考答案：Multi-Agent + RAG（且分阶段落地）

Q1 · 问答类？ 不是。是端到端"办事"，包含多个大环节。

Q2 · 有 SOP？ 主干有（分析 → 撰写 → 报价 → 合规），但每个环节内部 SOP 覆盖不同——招标公告分析比较模板化（工作流可覆盖），方案撰写高度依赖上一步的分析结论（需要动态决策）。

Q3 · 工具调用动态？ 是。报价评审要参考"该客户历史中标价 + 竞对最近报价 + 成本模型"，具体查哪些依赖前面环节的分析结果。

Q4 · 单 Agent 装得下？ 装不下。四个环节各自有：① 独立的知识库（政策库、方案模板库、历史标价库、合规红线库）；② 不同的权限（比如报价数据只能给内部授权用户）；③ 不同的输出格式（分析报告 / 方案文档 / 报价表 / 合规意见）。单 Agent 的 prompt 至少 5000 字以上，超过阈值。

Q5 · 演化路径：一期先做「招标公告分析 + 方案撰写」两个 Agent（Multi-Agent 最小可行组合）；二期加"报价评审 Agent"；三期加"合规审查 Agent"。给客户画清楚三期路线图。

结论：Multi-Agent（4 个专业 Agent + 1 个协调 Agent）+ RAG（挂 4 类知识库）。每个 Agent 内部可能还是工作流 + RAG 的组合——Multi-Agent 是最外层的编排架构，不是取代其他架构。

面试金句预埋："Multi-Agent 是政企场景的稀有选择——只有当单 Agent 承载不了业务分工、且不同角色需要知识和权限隔离时才用。多数客户不需要，需要的时候要敢用、也要敢分阶段推。"

💼 六、面试金句预埋

架构选型思维 "架构选型的第一原则是够用就好。工作流能搞定的坚决不上 Agent，单 Agent 能搞定的坚决不上 Multi-Agent。政企客户要的不是最炫的架构，是能上线、能验收、能被审计的架构。"
成本 & 稳定性意识 "Agent 的自主决策等价于输出不稳定。这在演示场景是加分项，在生产场景可能是致命弱点。我给客户设计架构时，永远先问一句：这个场景能接受两次结果不完全一样吗？不能接受，Agent 就不是首选。"
可演化性视角 "好的 AI 架构方案要写演化路径——现在为什么选 X，未来什么条件下升级到 Y。政企项目都是分期建设，一期方案里就把二期、三期的架构升级点标出来，是 FDE 给客户最实在的专业感。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. 「越智能的架构 = 越好」是错觉——越智能的架构 = 越贵 + 越不稳定 + 越难解释。政企场景下，稳定性 > 智能性。（工作流不是"low"，是"稳"。）

2. RAG 和 Agent 不在同一维度——RAG 是知识来源，Agent 是决策架构。一个 Agent 可以内嵌 RAG，一个工作流的节点也可以用 RAG。把它们当对立选项，就是没搞懂。（架构分层：知识层、决策层、执行层，各选各的。）

3. Multi-Agent 是「最后手段」不是「顶级选择」——一期能用单 Agent 跑通的，坚决不用 Multi-Agent。多智能体调通的时间是单智能体的 3 倍。（越复杂的架构，客户越难验收。）
