🎯 一、今日目标

导师说

前两天你会让模型输出中文、输出 JSON——但模型能干的事都在它自己的脑子里。它不知道今天日期、不知道你公司数据库里有啥、不能帮你发邮件、不能查供应商黑名单。

Function Calling 就是让模型伸出手的机制——你把"工具"（一个 Python 函数）注册给它，它需要时会主动"申请调用"，你的代码执行完把结果回填给它，它综合结果再回答用户。

今天最关键的一个认知：Function Calling 不是模型执行代码。模型只输出"我想调用哪个函数、传什么参数"的意图 JSON，真正执行还是你的代码干。搞清这一点，后面所有 Agent 编排都水到渠成。

  • 搞清 Function Calling 的 5 环工作机制——画得出流程图
  • 记住 「定义 · 意图 · 执行 · 回填 · 总结」 五段口诀
  • 会写一份 规范的 tool schema（name / description / parameters）
  • 能把 "物资评标 Agent" 加两个工具，完整跑通
  • 会诊断 "模型明明该调工具却没调" 的 3 类典型原因

📖 二、核心讲解

是什么：Function Calling 的 5 环工作机制

大白话——你先告诉模型"我这儿有几把工具，各自能干啥"，模型自己判断啥时候需要哪把。它把"想调用工具的意图"以 JSON 输出，你的代码接过来真去执行，把结果再喂回模型，模型看着结果给用户最终答案。

① 用户提问 ② 模型判断 "某供应商的黑名单状态？" ─▶ "我需要工具 query_blacklist" │ ▼ ③ 输出意图 JSON {"tool":"query_blacklist","args":{"id":"S001"}} │ ▼ ④ 你的代码执行 (查 MySQL / 调 API / 走缓存) │ ▼ ⑤ 结果回填 → 模型 {"in_blacklist": true, "reason": "..."} │ ▼ ⑥ 模型综合输出 "该供应商在黑名单中，原因：..."

关键认知——模型不执行任何代码。它只是"决策 + 组装参数"，执行永远在你的宿主环境里。这一点也是 Function Calling 相对"直接给模型代码执行权"最重要的安全边界。

环节谁在干PM 视角要盯什么
① 定义你（FDE）tool schema 写不写得清，直接决定模型能不能识别用哪个工具
② 意图模型模型输出 tool_calls，包含 name 和 arguments
③ 执行你（代码）参数校验、异常兜底、超时保护、审计日志
④ 回填你（代码）结果以 {"role":"tool", "tool_call_id":..., "content":...} 塞回 messages
⑤ 总结模型看到 tool 结果后再生成给用户的答案
□ □ □ Function Calling 五段口诀 □ □ □
定义 · 意图 · 执行 · 回填 · 总结
你给工具 · 模型申请 · 你执行 · 你回喂 · 模型说答

为什么：Function Calling 的三个大坑

🚨 坑 1 · 以为模型直接执行代码（安全模型完全错）

很多 PM 第一次听 Function Calling 就以为"模型能执行 Python"——立刻担心安全问题："那它会不会 rm -rf？会不会删库？"

真相：模型永远不执行任何代码。它只是输出一段"我想调 X 函数、参数是 Y"的 JSON。执行完全在你的代码里，你决定什么工具能给它调、参数怎么校验、什么权限能开。

这个认知不对，你就无法给客户讲清"AI Agent 到底安不安全"——而这是政企场景客户第一个必问的问题。

正确姿势：把 Function Calling 想成"模型是甲方，你的代码是乙方，模型下单，你决定接不接"。模型永远只在"下单"这一环，执行动作完全在你手里。

🚨 坑 2 · tool 定义写得模糊，模型不知道啥时候用

PM 常见错法 —— tool schema 写成这样：

{
  "name": "search",
  "description": "搜索",
  "parameters": {"query": {"type": "string"}}
}

然后你抱怨"模型 100 次里只有 20 次会调这个工具"。当然——你 description 只有"搜索"俩字，模型怎么知道啥时候该用？它看不到你脑子里的"是搜供应商还是搜合同"的场景想象。

正确姿势：description 要具体到"什么场景该用 + 输入什么 + 返回什么"三件事。比如："查询供应商黑名单状态。当用户询问某个供应商是否被列入黑名单、或需要在评标前做合规检查时使用。输入 supplier_id（供应商编号），返回是否在黑名单及原因。"

🚨 坑 3 · 忘记把工具结果回填，模型永远看不见

新手常犯的最坑 Bug —— 模型输出了 tool_calls，你的代码执行完拿到结果，但结果没塞回 messages 就直接结束了。用户看到的答案里模型可能还在说"我需要查询供应商信息"——因为它根本没看到你查完的结果。

Function Calling 是一个至少两轮的调用：第一轮模型说"我要调工具"，第二轮把结果喂回去让它总结。少了第二轮就等于问题只问了一半。

正确姿势：写代码时把"工具执行完 → 把结果作为 role=tool 的消息塞回 messages → 再调一次 API"这个模式写成一个循环，见下面动手代码。

🧭 PM 行动指南：Function Calling 落地 4 关

关 1 · 工具定义清晰：name 用动宾结构（query_supplier_blacklist）；description 写"什么场景用 + 输入 + 返回"；parameters 每个字段有 description 和类型。

关 2 · 参数校验：模型输出的 arguments 是不可信输入，用 Pydantic 或手动校验（供应商 ID 格式对不对、金额范围合不合理）。

关 3 · 执行沙箱：工具函数要只读优先；写操作（删数据、发邮件、下单）必须加人工二次确认或权限校验。

关 4 · 错误回填：工具执行失败要以结构化错误信息回填（{"error": "供应商不存在"}），让模型知道"这次调用失败了"，能自我修正或换一种做法。

怎么用：4 步搭出一个工具调用

1
定义 tool schema —— 用 JSON Schema 描述 name / description / parameters（含 required、enum、type、format）。description 是模型选工具的唯一依据，写清"什么场景用+输入+返回"三件事。
2
把 tools 传给 API —— client.chat.completions.create(..., tools=[...], tool_choice="auto")。auto 让模型自己决定；"required" 强制必调；{"type":"function","function":{"name":"X"}} 强制调 X。
3
检测 tool_calls，执行对应函数 —— 遍历 response.choices[0].message.tool_calls，按 name 分发到你的 Python 函数，json.loads(arguments) 拿参数。永远 try/except 兜底，永远校验参数。
4
结果作为 tool message 回填，让模型总结 —— 把执行结果拼成 {"role":"tool","tool_call_id":id,"content":json.dumps(result)}，加进 messages，再调一次 API，拿到模型的最终答案。

🛠️ 三、动手步骤：给"物资评标 Agent"加两个工具

导师说

下面这个案例是我在某大型央企物资评标场景里的真实简化版。评标专家看到一个供应商时经常需要查两件事：这家有没有黑名单记录、过往中过我们哪些标。你把这两件事包装成工具喂给模型，Agent 就能自动做初筛了。跟着做一遍，你就搭完了人生第一个"能调工具的 Agent"。

📌 案例 A · 跟做：物资评标 Agent + 两个工具（完整代码）
工具定义

两个工具（真实场景里会连数据库，这里用 mock 数据）：

  • query_supplier_blacklist(supplier_id) —— 查供应商是否在黑名单
  • query_past_contracts(supplier_id) —— 查过往中标合同记录
完整代码 · evaluation_agent.py
# -*- coding: utf-8 -*-
# evaluation_agent.py —— 物资评标 Agent（Function Calling 最小骨架）
import os, json
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

# ============ 【一】模拟数据库（生产环境要改成真实查询） ============
BLACKLIST_DB = {
    "S001": {"in_blacklist": True,  "reason": "2024 年因质量问题被列入 3 年黑名单"},
    "S002": {"in_blacklist": False, "reason": None},
    "S003": {"in_blacklist": True,  "reason": "2023 年围标被查处"},
}

CONTRACTS_DB = {
    "S001": [{"year": 2022, "project": "A 项目", "amount": 3000000}],
    "S002": [{"year": 2023, "project": "B 项目", "amount": 5000000},
             {"year": 2024, "project": "C 项目", "amount": 8000000}],
    "S003": [],
}

# ============ 【二】工具实现（真正干活的 Python 函数） ============
def query_supplier_blacklist(supplier_id: str) -> dict:
    """查供应商黑名单"""
    if supplier_id not in BLACKLIST_DB:
        return {"error": f"供应商 {supplier_id} 不存在"}
    return BLACKLIST_DB[supplier_id]

def query_past_contracts(supplier_id: str) -> dict:
    """查过往合同"""
    if supplier_id not in CONTRACTS_DB:
        return {"error": f"供应商 {supplier_id} 不存在"}
    contracts = CONTRACTS_DB[supplier_id]
    return {
        "supplier_id": supplier_id,
        "total_count": len(contracts),
        "total_amount": sum(c["amount"] for c in contracts),
        "contracts": contracts,
    }

# 路由表：模型说要调哪个 name，就找对应函数
TOOL_ROUTER = {
    "query_supplier_blacklist": query_supplier_blacklist,
    "query_past_contracts": query_past_contracts,
}

# ============ 【三】tool schema（模型看这个决定用哪个） ============
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "query_supplier_blacklist",
            "description": (
                "查询供应商是否在黑名单中。"
                "当用户询问某个供应商的合规状态、评标前的合规检查、"
                "或提到'黑名单''违规记录'时使用。"
                "返回是否在黑名单及原因说明。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "supplier_id": {
                        "type": "string",
                        "description": "供应商编号，格式如 S001、S002",
                    }
                },
                "required": ["supplier_id"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "query_past_contracts",
            "description": (
                "查询供应商过往中标合同记录。"
                "当用户询问'合作历史''以前中过什么标''累计金额'时使用。"
                "返回合同数量、总金额、每条合同的年份/项目/金额。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "supplier_id": {"type": "string", "description": "供应商编号"}
                },
                "required": ["supplier_id"],
            },
        },
    },
]

SYSTEM = """你是物资评标助手，帮评标专家做供应商合规初筛。
- 用户提到某个供应商时，主动查黑名单和历史合同
- 结论要明确：建议通过 / 建议慎用 / 建议排除
- 每个结论后面写清依据"""

# ============ 【四】主循环：处理 tool_calls 到最终答案 ============
def run_agent(user_question: str, max_rounds: int = 5) -> str:
    """处理一次对话，直到模型给出最终答案"""
    messages = [
        {"role": "system", "content": SYSTEM},
        {"role": "user",   "content": user_question},
    ]

    for round_idx in range(max_rounds):
        resp = client.chat.completions.create(
            model="qwen-plus",
            messages=messages,
            tools=TOOLS,
            tool_choice="auto",        # 让模型自己决定要不要用工具
            temperature=0.1,
        )
        msg = resp.choices[0].message

        # 情况 1：模型不用工具，直接给答案 → 结束
        if not msg.tool_calls:
            return msg.content

        # 情况 2：模型申请调用一个或多个工具
        messages.append(msg)           # 【关键】把模型的 assistant 消息塞回历史
        for tc in msg.tool_calls:
            name = tc.function.name
            args = json.loads(tc.function.arguments)
            print(f"[第 {round_idx+1} 轮] 模型申请调用 {name}({args})")

            # 【关键】参数校验（简版）
            if name not in TOOL_ROUTER:
                result = {"error": f"未知工具 {name}"}
            else:
                try:
                    result = TOOL_ROUTER[name](**args)
                except Exception as e:
                    result = {"error": f"{type(e).__name__}: {e}"}

            # 【关键】把结果作为 role=tool 的消息回填
            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,
                "content": json.dumps(result, ensure_ascii=False),
            })
        # 继续下一轮，让模型看到工具结果后总结

    return "⚠️ 达到最大轮次仍未收敛，请人工介入"

# ============ 【五】跑一个真实问题 ============
if __name__ == "__main__":
    q = "供应商 S001 这次投标了，你帮我看看能不能过评审？"
    print(f"\n【用户】{q}")
    print(f"\n【Agent】{run_agent(q)}")
预期运行输出
【用户】供应商 S001 这次投标了，你帮我看看能不能过评审？

[第 1 轮] 模型申请调用 query_supplier_blacklist({'supplier_id': 'S001'})
[第 1 轮] 模型申请调用 query_past_contracts({'supplier_id': 'S001'})

【Agent】建议排除。依据：
- 黑名单状态：S001 在黑名单中，原因是 2024 年因质量问题被列入 3 年黑名单。
- 历史合作：过往仅 1 次中标（2022 年 A 项目，300 万元）。
- 结论：黑名单一票否决，本次评审建议排除该供应商。
你要盯住的 4 个关键点
  1. 模型自动并行调用两个工具——一次 tool_calls 里可能有多个，要循环处理。
  2. assistant 消息必须回塞历史（messages.append(msg)），否则模型下轮不知道自己申请过啥。
  3. tool 消息的 tool_call_id 必须对应——OpenAI 兼容协议靠这个把结果匹配回请求。
  4. max_rounds 兜底——防止模型陷入"调工具→调工具→调工具..."的无限循环（真发生过）。
✅ 你今天做完了什么
你搭出了一个能自主查数据、自主判断、自主给结论的 Agent 骨架。虽然还很简陋，但"模型 → 工具 → 数据库 → 答案"这一整条闭环已经打通。Day 7 你会在这个骨架上加 RAG，Day 8+ 就是完整 Agent 编排了。
🧪 案例 B · 自练 1：给"员工问答 Agent"加"查请假余额"工具

需求：HR 场景 —— 员工问"我还剩几天年假？"，Agent 要调用工具查该员工的请假余额，返回具体天数。

提示：

  1. tool name 建议 query_leave_balance；
  2. 参数：employee_id（string），可选 leave_type（枚举：annual/sick/personal）；

查看参考实现要点 
{
    "type": "function",
    "function": {
        "name": "query_leave_balance",
        "description": (
            "查询指定员工的请假余额（年假/病假/事假天数）。"
            "当员工询问'我还剩几天假''请假余额''休假额度'时使用。"
            "如果员工没说自己的工号，不要瞎调，先反问工号。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "employee_id": {"type": "string", "description": "员工工号，格式 EMP+6位数字"},
                "leave_type": {
                    "type": "string",
                    "enum": ["annual", "sick", "personal", "all"],
                    "description": "假期类型，all 表示查所有类型",
                    "default": "all"
                }
            },
            "required": ["employee_id"]
        }
    }
}

# SYSTEM 里一定要加一句：
# "查请假余额前，如果不知道员工工号，先反问，不要瞎调工具"

关键点 1：用 enum 限死可选值；关键点 2：用 default 兜底缺省；关键点 3：system prompt 显式教模型"缺参数就反问"，别调空工具。

🧪 案例 C · 自练 2：Bug case——模型该调工具却不调

场景：某同事写了个"IT 运维助手 Agent"，工具是"查服务器 CPU 使用率"，可是模型经常自己瞎编一个数字回答用户，就是不调工具。他的定义长这样：

SYSTEM = "你是 IT 运维助手，回答用户问题。"

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_cpu",
        "description": "获取 CPU",
        "parameters": {
            "type": "object",
            "properties": {"h": {"type": "string"}}
        }
    }
}]

client.chat.completions.create(model="qwen-plus", messages=[...], tools=TOOLS)
# 用户问："server-01 现在 CPU 多少？"
# 模型："当前 CPU 使用率约 45%"  ← 编的！根本没调工具

请诊断：3 类典型问题分别是什么？怎么修？

查看参考答案

原因 1 · description 太抽象——"获取 CPU"三个字模型看不出啥场景该用、要传啥、返回啥。修复：写"查询指定服务器当前 CPU 使用率。当用户询问服务器负载、CPU 状态、性能监控时使用。输入 hostname（服务器名，如 server-01），返回 0-100 的百分比。"

原因 2 · 参数名字 h 无语义 + 没有 description——模型看到 h 完全不知道该塞啥。修复：改名 hostname，加 description "服务器主机名，如 server-01"，加到 required。

原因 3 · system prompt 里没提示可用工具、没禁止编造——模型天生倾向"直接回答"而不是"调工具"，如果不主动提示它就会走幻觉路线。修复：SYSTEM 里加 "查询实时数据（CPU、内存、日志）必须调工具，不允许编造数值。"

合计修复后：模型会稳定调用工具。

面试金句预埋："Function Calling 模型不调工具的三大原因——description 太抽象、参数无语义、prompt 没教它优先调工具。三处修完，调用率从 30% 到 95%。"

🔍 Function Calling vs Agent 一句话区别
Function Calling能力——模型能输出"我想调哪个工具"的意图。是零件。
Agent系统——用 Function Calling + 循环调度 + 记忆 + 规划构成的整体。是成品。

📝 五、5 题小测验

先想 30 秒再翻答案。错项解析比正确答案更值钱。

Q1 · 关于 Function Calling 的执行边界，下列说法正确的是？
  • A. 模型直接执行你注册的 Python 函数，所以有安全隐患
  • B. 模型只输出"想调用哪个工具、传什么参数"的意图 JSON，真正执行在你的代码里
  • C. 模型会自动连接你的数据库并执行 SQL
  • D. 需要给模型开 shell 权限才能用 Function Calling
✅ 答案：B

Function Calling 的核心安全模型就是"模型出意图、代码来执行"。模型永远不接触你的数据库、你的文件、你的网络。这是 FDE 给政企客户讲清安全边界的关键——模型是"下单人"，代码是"操作员"，权限完全在你手里。

❌ 错项解析

A 错在把"输出意图"当成"执行代码"——很多 PM 第一反应是这个误解，跟客户讲 Agent 安全性时会犯同样的错。C 完全脱离事实——模型没有任何数据库连接能力，SQL 也是你的代码去执行。D 错在混淆了 Function Calling 和 Code Interpreter——后者是另一种能力（沙箱内执行代码），Function Calling 从不需要 shell。

Q2 · Function Calling 五段口诀是？
  • A. 请求 · 响应 · 解析 · 兜底 · 部署
  • B. 定义 · 意图 · 执行 · 回填 · 总结
  • C. 模型 · Prompt · 工具 · 数据 · 结果
  • D. 输入 · 处理 · 输出 · 校验 · 回滚
✅ 答案：B

定义（你写 schema）→ 意图（模型出 tool_calls）→ 执行（你的代码跑）→ 回填（结果塞回 messages）→ 总结（模型看到结果给答案）。五个环节缺一不可，尤其是"回填"这一环，新手最容易漏。

❌ 错项解析

A 是普通 HTTP 请求的通用套路，没体现 Function Calling 独有的"模型-代码交互闭环"。C 是要素罗列，不是动作顺序。D 是软件工程通用流程，缺"意图"和"回填"这两个关键环节，没抓住 Function Calling 的精髓。

Q3 · 模型明明该调工具却不调，最可能的三大原因？
  • A. 模型太笨 / API 有 bug / 网络不稳
  • B. description 太抽象 / 参数字段无语义没 description / system 里没提示优先调工具
  • C. 温度太低 / max_tokens 太小 / 没开流式
  • D. Key 权限不够 / 模型档次不够高 / 需要付费
✅ 答案：B

这是 Function Calling 落地时 90% 案例的三大真凶。修 description 让模型知道"什么场景用"；修参数字段让模型知道"传什么"；修 system 引导让模型优先调工具而不是幻觉编答。三处一改，调用率一般能从 30% 拉到 95%。

❌ 错项解析

A 是甩锅思维——把工程问题归到"模型笨"，回避了 FDE 的责任。C 完全无关——温度和 max_tokens 影响输出风格但不决定是否调工具。D 错在归因方向——qwen-plus / gpt-4o mini 都完全支持 Function Calling，档次不够是错觉。

Q4 · 模型在一轮里输出了 3 个 tool_calls（并行请求），正确处理是？
  • A. 只处理第一个，忽略其他两个
  • B. 全部循环处理，每个都执行完把结果作为一条 tool 消息回填，然后再调一次 API
  • C. 报错给用户："模型申请太多工具"
  • D. 拒绝并行，Prompt 里强制模型一次只调一个
✅ 答案：B

并行 tool_calls 是现代 LLM 的标准能力——用户一句话可能触发多个查询（如 "S001 的黑名单 + 历史合同"）。正确做法是全部执行，全部回填，再让模型综合总结。回填时每个 tool 结果对应各自的 tool_call_id——这是 OpenAI 兼容协议匹配请求和结果的方式。

❌ 错项解析

A 是最常见的新手 Bug——只处理第一个 tool_call 会让模型永远看不到其他工具的结果，导致答案不完整或幻觉。C 错在把模型的合理并发当成异常。D 是自废武功——强制串行会让 Agent 延迟翻倍，本来能一次调完的事拆成 3 轮。

Q5 · 综合题——你为政企做一个"合同风险扫描 Agent"，涉及 3 个工具（查客户信用/查历史违约/发预警邮件），最应该怎么设计安全边界？

简答，写出关键设计点。

✅ 参考答案

1 · 工具权限分级：查询类工具（查信用、查违约）只读 → 直接给模型调；写操作类工具（发预警邮件）→ 必须加人工二次确认（模型只是提议，人点"确认"才真发）。

2 · 参数校验：模型输出的 arguments 是不可信输入，用 Pydantic 强校验（客户 ID 格式、邮件收件人白名单、邮件正文长度上限）。

3 · 审计日志：每次 tool 调用记录 tool_name / arguments / result / 触发的 user_query / timestamp。政企合规审计必备，也是 Debug 的救命稻草。

4 · 限速与配额：发邮件工具单次运行调用上限（比如 5 封/次），防止模型抽风批量骚扰客户。

5 · max_rounds 兜底：Agent 循环最多 5 轮，超出人工介入。防止无限调工具的僵尸循环。

6 · 错误结构化回填：工具失败以 {"error": "..."} 回填，让模型知道"失败了"，可能换个工具或告诉用户"这一步查不到"。

面试金句预埋："Agent 的安全从来不是 Prompt 层的说服，是代码层的权限设计——只读工具可以给模型调，写操作必须人工二次确认。"

💼 六、面试金句预埋

Function Calling 的定位 · 分水岭 "Function Calling 是从'模型只会说'到'模型会干活'的分水岭。它把 LLM 从聊天机器人变成能查数据、能调 API、能真做事的执行主体。但要记住它的边界——模型只出意图，执行永远在你的代码里。这一点讲不清，客户就不敢让 Agent 上线。"
工具设计思维 · description 决定命中率 "我给团队立的规矩——tool 的 description 必须写清三件事：什么场景用、输入什么、返回什么。见过太多同事把 description 写成'查询数据'四个字，然后抱怨模型不调工具。改一次 description 从 30% 调用率干到 95% 是常态。description 就是工具的'广告词'，模型看这个决定用不用。"
可观测性 · 每次工具调用都要留痕 "生产 Agent 必须做的是全链路可观测——每次 tool_calls 的 name、arguments、result 都要打日志。政企审计要用、Debug 要用、PM 复盘也要用。没有可观测性的 Agent 就是黑盒，出事只能背锅，讲不清是模型的问题还是工具的问题。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. Function Calling 不是"模型执行代码"——模型只出意图，代码来执行。（安全边界的第一课，PM 讲客户方案必须清楚。）

2. 模型不调工具 90% 都是你 description 写得不清楚，不是模型笨。（写 description 就是写工具的广告词，写得好模型就买账。）

3. tool 消息必须严格回填 messages——漏了这一步模型永远看不到结果。（新手最常犯的 Bug，也是 Agent 骨架的核心。）
