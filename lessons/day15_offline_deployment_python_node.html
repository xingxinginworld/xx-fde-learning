📖 二、核心讲解

是什么：离线部署的 3 层困难

大白话——离线环境不是"网速慢"，是网络物理隔绝、可能连你的电脑都不能连。分 3 层困难：

困难层表现典型翻车
① 依赖装不上pip/npm 联不上镜像源装了半天报 "Could not find a version"
② 网络访问不到调外部 API、拉模型、下 HuggingFace 全断模型没下载完程序起不来
③ 权限不够非 root 用户、SELinux、防火墙、开机自启手动能跑，重启就没了；日志写不进指定目录

反直觉的地方：90% 的翻车不是代码 bug，是环境不一致。同事的 macOS、你的 Windows 装了 Python 3.11 + M 系列 wheel，客户是 CentOS 7 + Python 3.6 + x86_64——三层都对不上，包装不上是必然。

□ □ □ 离线部署五步口诀 □ □ □
打 · 传 · 装 · 启 · 守
依赖打包 · 传输 · 安装 · 启动 · 守护 — 少任何一步都翻车

为什么：FDE 视角下的三个大坑

🚨 坑 1 · 只 pip freeze > requirements.txt 就以为够了

requirements.txt 只记录了 Python 包，没记录：系统级 apt 依赖（gcc/libpq-dev/ffmpeg）、CUDA 驱动、GLIBC 版本、字体、时区、SSL 证书。

典型翻车：你在 Ubuntu 22 上跑得好好的，客户 CentOS 7 装 psycopg2 需要 libpq-dev，装 Pillow 需要 libjpeg，装 opencv-python 需要 libGL.so.1——这些都不在你的 requirements.txt 里。到现场才发现，加起来又是半天。

正确姿势：除了 requirements.txt，另外维护一份 system-deps.md，列出所有 apt install / yum install 的系统包，且注明用途。

🚨 坑 2 · 依赖包直接 zip 复制——二进制平台差异翻车

Python wheel 包有平台差异：numpy-1.24-cp310-cp310-macosx_11_0_arm64.whl 只能在 macOS ARM64 装，numpy-1.24-cp310-cp310-manylinux2014_x86_64.whl 才能在 Linux x86 装。你在 Mac 上 pip download 默认拉的是 Mac 版，复制到 CentOS 就是废纸。

正确姿势：下载时 显式指定目标平台——
pip download -r requirements.txt -d ./wheels --platform manylinux2014_x86_64 --python-version 3.10 --only-binary=:all:

Node 类似——npm pack 出的是通用 tar 包，但如果依赖了 node-sass、sharp 这类含 native binding 的包，也要在目标平台重新构建，或用 npm ci --offline 且预先在同架构机器打包。

🚨 坑 3 · 不预演在类似的隔离环境测——现场发现装不上就是灾难现场

客户现场机会难得，一次不行下次可能要一周后。你到现场才发现装不上，客户信息部长脸色难看，你还得排队等他给你放行申请。

正确姿势：去客户现场之前，在自己电脑上开一台 干净同架构 VM（例如 VMware 或 Docker 里的 CentOS 7），断网，用你打的包 从零装一遍。所有报错在这里踩完，再出门。

🧭 PM 行动指南：离线部署前必做 4 件事

Step A · 拉一台干净同架构机器预演——问客户要目标机器的 uname -a、cat /etc/os-release、python3 --version、GPU/CUDA 版本。自己搭同版本 VM 或容器。

Step B · 系统依赖列清单——除 requirements.txt 外，写一份 system-deps.md：GLIBC / gcc / CUDA / ffmpeg / libpq / 字体 / 时区，逐项标"必需 / 可选 / 备用"。

Step C · 依赖打包指定平台——pip download --platform manylinux2014_x86_64 --python-version 3.10 --only-binary=:all:，Node 用 npm pack 或 verdaccio 私有镜像。

Step D · 起手 SOP 手册——手册要写到"客户运维小张只会 Ctrl+C/V"的程度：每一步是一行命令、预期输出、报错怎么办。

怎么用：五步完成离线 Python/Node 部署

1
依赖打包（打）——在有网机器上：
pip download -r requirements.txt -d ./wheels --platform manylinux2014_x86_64 --python-version 3.10 --only-binary=:all:
npm：npm pack <pkg> 逐个打，或起 verdaccio 私有镜像预缓存全部依赖后 tarball 出来。
关键：把 Python 解释器本身也打进去（python-3.10.13-amd64.tar.xz），别指望客户机器已经有对版本。
2
传输到客户机器（传）——三种方式：
· 堡垒机 SCP——央国企多数走这条，速度慢但合规。
· U 盘导入——最后手段，先申请审批，且介质要过防病毒扫描。
· OSS 内网桶——客户如有内网对象存储最省事，走内部专线。
关键：把包分卷压缩（tar -czf - dir | split -b 500M）避免大文件传输失败要重来。
3
离线安装（装）——目标机器上：
pip install --no-index --find-links=./wheels -r requirements.txt
npm：npm install --offline --prefer-offline，或提前 npm ci --cache ./npm-cache --prefer-offline。
关键：--no-index 强制不走网络，否则 pip 会尝试连 pypi.org 卡住。
4
服务启动（启）——写一份启动脚本 start.sh：
#!/bin/bash
export PYTHONPATH=$(pwd)
export TZ=Asia/Shanghai
nohup python -m uvicorn app:app --host 0.0.0.0 --port 8000 > logs/app.log 2>&1 &
关键：日志目录、端口、时区、环境变量在这一层固定，别让客户运维猜。
5
守护（守）——写 systemd 单元让服务开机自启、崩溃重启：
[Service]
Type=simple
ExecStart=/opt/app/start.sh
Restart=always
RestartSec=5
关键：客户机器一年可能因运维重启 5-10 次，没 systemd 你的服务就是"死一次要你上门一次"。

📌 案例 A · 把 FastAPI + Streamlit RAG Demo 部署到离线 CentOS 7（跟着做）
目标环境

CentOS 7.9 · Python 3.10（客户机器只有 Python 3.6，需要自带）· 8G 内存 · 无 GPU · 无外网。

Step 1 · 在你办公室机器上（有网）打包
# 1.1 建干净虚拟环境
python3.10 -m venv .venv && source .venv/bin/activate

# 1.2 生成锁定版本
pip freeze > requirements.txt

# 1.3 下载所有依赖（关键 —— 显式指定 Linux 平台）
pip download -r requirements.txt \
  -d ./wheels \
  --platform manylinux2014_x86_64 \
  --python-version 3.10 \
  --only-binary=:all:

# 1.4 下载 Python 解释器本体
wget https://www.python.org/ftp/python/3.10.13/Python-3.10.13.tgz

# 1.5 打个 tar 包
tar -czf offline-rag-demo.tar.gz wheels/ Python-3.10.13.tgz app/ start.sh system-deps.md README.md
Step 2 · 传输

走客户堡垒机 SCP。分卷压缩以防大文件传输中断：
split -b 500M offline-rag-demo.tar.gz part_

Step 3 · 客户机器上离线安装
# 3.1 合并分卷
cat part_* > offline-rag-demo.tar.gz && tar -xzf offline-rag-demo.tar.gz

# 3.2 先装系统依赖（提前和客户运维协调好 yum 本地源）
sudo yum install -y gcc openssl-devel bzip2-devel libffi-devel

# 3.3 编译安装 Python 3.10
tar -xzf Python-3.10.13.tgz && cd Python-3.10.13
./configure --prefix=/opt/python310 --enable-optimizations
make -j4 && sudo make altinstall

# 3.4 建虚拟环境 + 离线装依赖
/opt/python310/bin/python3.10 -m venv .venv
source .venv/bin/activate
pip install --no-index --find-links=./wheels -r requirements.txt
Step 4 · 启动与守护

写 start.sh 和 rag-demo.service（systemd unit），systemctl enable rag-demo && systemctl start rag-demo。

可能翻车的 5 个地方（预防清单）
  • ① GLIBC 版本太老（CentOS 7 是 2.17，PyTorch 2.x 要求 ≥ 2.24）→ 换 CentOS 7 兼容的 PyTorch 1.13 版本，或让客户升级到 CentOS Stream 8
  • ② SSL 证书缺失（HTTPS 请求报 SSLError）→ 打包时把 certifi 一起打，或复制系统 CA
  • ③ 中文乱码（UnicodeDecodeError）→ 设置 LANG=zh_CN.UTF-8 和 PYTHONIOENCODING=utf-8
  • ④ 端口被防火墙拦→ 提前跟客户运维要 firewall-cmd 开放 8000 端口
  • ⑤ SELinux 阻止服务写日志→ setenforce 0 临时关闭，或写 audit2allow 策略

🧪 Bug case · 离线机器 pip install 报 "Could not find a version"（自己练）

现场：你按案例 A 步骤操作到 Step 3.4，敲 pip install --no-index --find-links=./wheels -r requirements.txt，报错：
ERROR: Could not find a version that satisfies the requirement lxml==4.9.3

3 种可能原因分别是什么？怎么排查？

查看参考答案

原因 1 · 平台不匹配——你打包时用的是 macOS，下载的是 lxml-4.9.3-cp310-cp310-macosx_11_0_arm64.whl，但客户是 Linux x86_64。
排查：ls ./wheels/lxml*，看文件名里的 manylinux 或 macosx；解决：重新在有网机器 pip download --platform manylinux2014_x86_64。

原因 2 · Python 版本不匹配——你打包时指定的是 Python 3.10（cp310），但客户机器实际用的是 Python 3.9（cp39）。
排查：python --version 看客户实际版本；解决：要么客户升级 Python，要么重新 --python-version 3.9 打包。

原因 3 · 只下了源码没下二进制——某些包（尤其含 C 扩展的，如 lxml、psycopg2）默认只发 sdist 源码，需要 --only-binary=:all: 强制拉预编译 wheel。你如果没加这个参数，可能只下了 lxml-4.9.3.tar.gz，离线机没有编译工具装不了。
排查：看 wheels 目录里是 .whl 还是 .tar.gz；解决：加 --only-binary=:all:，或在离线机装 gcc + python-devel 让它现场编译。

面试金句："离线 pip 报错先看 ls wheels/，文件名里的 manylinux/macosx、cp310/cp39、.whl/.tar.gz 三个片段决定错在哪一层。"

🚨 离线部署翻车 Top 10（保命清单）
  1. Python 版本不匹配——打包指定 3.10，客户机器只有 3.6/3.9
  2. GLIBC 版本太老——CentOS 7 的 GLIBC 2.17 装不上新版 PyTorch
  3. SSL 证书缺失——离线机无系统 CA，HTTPS 请求全 fail
  4. 时区错乱——UTC 时区导致日志时间对不上

  7. 端口占用/防火墙——8000 端口被占，或 firewalld 拦

📝 五、5 题小测验

建议先自己想 20 秒再点开答案。答错也别慌——错项解析比正确答案更值钱。

Q1 · 你在 Mac 上执行 pip download -r req.txt -d ./wheels，然后传到 CentOS 装，报"Could not find a version"，最可能原因？
  • A. requirements.txt 版本号写错了
  • B. 下的包是 macOS ARM64 版本，Linux 装不上
  • C. CentOS 上 Python 没装
  • D. 网络还是在偷偷走 pypi
✅ 答案：B

没加 --platform manylinux2014_x86_64，pip 默认按当前机器（Mac ARM）下载。同版本号的包，wheel 文件的 platform tag 不匹配就装不上。

❌ 错项解析

A 如果版本号写错，报错是 "No matching distribution"，措辞不同。C 如果 Python 没装，根本调不起 pip，报的是 command not found。D 如果网络在走，报的是 "Connection timeout"，不是 "Could not find a version"。

Q2 · "打·传·装·启·守" 里，「守」这一步的核心目的是？
  • A. 让服务比别人跑得快
  • B. 让服务开机自启、崩溃自动重启
  • C. 让服务日志更详细
  • D. 让服务连不上外网
✅ 答案：B

「守」= 守护进程。客户机器一年可能重启 5-10 次（补丁/演练/断电），没 systemd 你的服务重启后就没了，客户要打电话给你上门重启，你在某公司某单位驻场应该体会过这种活多痛苦。

❌ 错项解析

A 性能不是"守"关注的——性能是启动参数（worker 数、并发数）的事。C 日志详细度是 logging 配置的事，不是 systemd。D 完全无关，且离线环境本来就断外网。

Q3 · 客户机器是 CentOS 7，你打的 PyTorch 2.1 装完 import torch 报 GLIBC 版本不够，怎么办？
  • A. 让客户升级 GLIBC（把 GLIBC 拷过去替换）
  • B. 换成兼容的 PyTorch 1.13 版本
  • C. 强行 ldconfig 一下
  • D. 让客户重装 CentOS 8
✅ 答案：B

PyTorch 2.x 要 GLIBC ≥ 2.24，CentOS 7 是 2.17。合理选择是回退到 PyTorch 1.13（兼容 GLIBC 2.17），或让客户长期规划升级到 CentOS Stream 8/9。

❌ 错项解析

A 是灾难操作——GLIBC 是系统底层，暴力替换会让整个系统的其他程序全崩，甚至开不了机。生产系统这种操作要挨批。C ldconfig 只是刷新链接缓存，解决不了版本问题。D 重装系统对已经跑着别的业务的客户是灾难，你没那个权限也没那个必要。

Q4 · 离线部署前你要问客户运维要哪几个关键信息？
  • A. 操作系统版本 + Python 版本 + CPU 架构
  • B. 操作系统版本 + Python 版本 + CPU 架构 + GPU/CUDA + GLIBC 版本 + 是否有 root
  • C. 只要客户 IP 就行
  • D. 让客户运维准备好一个能上网的机器
✅ 答案：B

预演的目的就是在自己 VM 里搭出和客户机器一模一样的环境。这 6 项少任何一项都可能翻车——尤其 GLIBC 版本和 root 权限，前者决定能不能装 PyTorch，后者决定能不能装 systemd unit。

❌ 错项解析

A 少了 GLIBC 和权限，是最常见的疏漏。C 只有 IP 完全不够——你连能不能装 Python 都不知道。D 是幻想——离线环境本质就是没网，让客户给你一台联网机是变相不做离线部署。

Q5 · 综合题——客户运维凌晨 3 点电话："你那服务重启后起不来"。你怎么远程指挥他排查？

按逐层排查思路写下你的话术。

✅ 参考答案：三层排查法

第一层 · 服务层——让他敲：systemctl status rag-demo，看服务是否 activated；journalctl -u rag-demo -n 100，看最后 100 行日志。90% 的问题这一步就能定位。

第二层 · 依赖层——如果 systemd 说服务启动失败，让他手动跑：source .venv/bin/activate && python -c "import torch, fastapi"，看是否有 import 错误。多半是升级过 Python 或某个依赖被误删。

第三层 · 环境层——如果 import 正常但服务连不上，看端口和防火墙：ss -tlnp | grep 8000 看端口占用；firewall-cmd --list-ports 看防火墙。

话术："张老师您别急，我引导您三步：第一步敲这个看输出发我截图；第二步这样这样；第三步这样。90% 从这三步定位。"

面试金句："离线部署交付质量看两个指标——SOP 手册薄不薄（薄好），凌晨电话次数多不多（少好）。"

💼 六、面试金句预埋

预演文化 "离线部署我从来不带着 Demo 直接去客户现场。去之前先在自己 VM 里搭一台一模一样的机器，断网从零装一遍。所有报错在这里踩完，现场只做已经验证过的流程。这么干过一次，现场翻车率能从 50% 降到 5%。"
平台匹配意识 "pip download 我从来加三个参数——--platform、--python-version、--only-binary=:all:。这三个参数不加，一定翻车。这不是知识点，是我一次现场被客户信息部长骂了两小时之后刻在骨头上的肌肉记忆。"
零基础可运维 "我写的 SOP 手册标准是——让一个只会 Ctrl+C/V 的客户运维能独立跑起来。每一步一行命令、预期输出、报错怎么办。这才叫交付。不然客户永远拴着你，你出差费比 API 还贵。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. "requirements.txt + pip install" 只是完成了 20% 的离线部署——系统依赖、Python 解释器、CUDA、字体、时区，这些才是大头。

2. 依赖包是有平台的。Mac 打的包 Linux 装不上，跟"文件复制过去应该都能用"的直觉完全相反。

3. 没有 systemd 的部署等于半成品——客户机器一定会重启，你的服务一定要能起得来。
