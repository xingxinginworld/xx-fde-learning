🎯 一、今日目标

导师说

Day 1 判断"该不该做"，Day 2 决定"用哪种架构"，今天要落到把这两天的结论写成一份能签合同的文档。这是 FDE 交付链最赚钱的一环——PPT 给客户看的动作，方案文档给开发看的细节，Token 估算给采购看的账本。三件事必须在同一份文档里搞定。

你 PM 老本行写过很多方案，但 AI 方案有一个不一样的地方——它有推理成本。传统项目上线后成本是固定的，AI 项目每一次调用都在花钱。这就是为什么方案文档里必须有 Token 估算章节，你算不清就等着一年后被采购追杀。

今天最重要的一件事：算 Token 不是数学题，是采购谈判的筹码。你把公式和三档规模算出来，客户想砍你还得先说服自己的采购。

  • 掌握 AI 项目方案文档的 6 段结构，一份文档同时通过客户 / 开发 / 合规三方审查
  • 会用 「Token 估算公式 + 三档规模法」，把成本算到月度级并给出扩展性说明
  • 看懂主流大模型 输入 / 输出单价差异，能给客户做「模型选型 × 成本」对比表
  • 识别方案文档里 5 个高频坑点，写完自检不翻车

📖 二、核心讲解

是什么：AI 项目方案文档的 6 个必要段

大白话——方案文档不是给一个人看的，是给三拨人看的：客户业务方看背景和验收，客户 IT 方看架构和风险，开发 leader 看数据方案和成本。三方视角都要照顾到，缺一段就有一方"看不下去 / 不认账"。

段号 段落名 主要给谁看 核心要回答的问题
①需求背景与目标客户业务方 · 老板为什么要做？做成什么样算成功？（量化指标）
②技术方案（架构图+组件选型）客户 IT · 开发 leader用什么架构？为什么不用其他架构？（承接 Day 2）
③数据方案（数据源+预处理+存储）客户 IT · 数据合规数据从哪来？怎么处理？存哪儿？合规吗？
④Token/成本估算客户采购 · 财务一年花多少钱？三档规模分别多少？扩容成本？
⑤风险与替代方案客户 IT · 项目 PMO可能翻车的点？翻车了怎么办？
⑥里程碑与验收客户 PMO · 开发 leader什么时候交付什么？怎么算验收通过？

反直觉的地方：很多 PM 觉得写完 ①②③ 就够了，把 ④⑤ 一笔带过。恰恰是 ④⑤ 决定客户签不签合同——签合同的是采购和 PMO，他们看的就是账本和风险。

背景 · 方案 · 数据
成本 · 风险 · 里程碑
六段齐 · 客户签 · 开发不挑刺 · 采购不砍价

为什么：三个把方案搞崩的高频误区

🚨 误区 1 · 只写 PPT 不写细节文档（"开发按 PPT 猜就翻车"型）

你给客户做了一份漂亮 PPT，标了架构图、写了亮点，客户签了合同。开发拿到 PPT 一看——"数据源到底哪几张表？预处理规则是什么？RAG 切片粒度多少？"你答不上来，开发按自己理解写代码，交付时和客户预期对不上，二次返工。

PPT 和方案文档是两个物种。PPT 给客户高层看观感，方案文档给客户 IT + 开发看落地细节。签合同前必须有方案文档，PPT 只是它的浓缩视图。

正确姿势：PPT ≤ 15 页做售前沟通，方案文档 15-40 页做交付依据。方案文档一定要在合同附件里出现，否则出问题时你没抓手。

🚨 误区 2 · Token 成本拍脑袋（"一年后账单出来客户想砍你"型）

方案里写"预计月度推理成本约 5000 元"——问依据，你说"感觉差不多"。上线三个月一算，实际是 3.8 万 / 月，是估算的 7 倍多。客户马上把责任推给你："当初你说 5000，现在为什么这么多？"

AI 成本翻倍不是意外，是常态——大家习惯低估的原因有三个：① 忘了算系统 prompt 和 few-shot 的固定开销（每次调用都在花）；② 忘了算 RAG 检索出来的上下文 token（可能比问题本身还长）；③ 忘了算失败重试（幻觉纠错、格式校验失败要重试）。

正确姿势：用「Token 估算公式」+ 「三档规模法」（低 / 中 / 高日均调用量）算出三个数字给客户看。任何单一数字都是陷阱。

🚨 误区 3 · 不写风险与替代方案（"问题发生时全责在你"型）

项目上线两周，模型效果不达预期，客户暴怒："方案里没提这个风险，那就是你能力问题，你自己扛。" 你打开方案文档，风险章节写着一句"技术风险可控" —— 完蛋了，这句是"你自己扛"的自证。

风险章节的作用不是显得你懂技术，是提前和客户建立"风险共担"的心理契约。写清楚"XX 场景可能准确率不达 90%，届时启用兜底策略 Y"—— 这句话上线后能救你的命。

正确姿势：至少写 3 类风险（模型效果 / 成本超支 / 合规变动），每类都配替代方案。风险不是坏话，是你的责任边界。

🧭 PM 行动指南：方案文档写完必过 3 个人

P1 · 客户业务 leader——看①⑥。问 TA："你看完①，觉得我们真的懂你要什么吗？⑥ 的验收标准你能接受吗？"

P2 · 客户 IT / 架构师——看②③⑤。问 TA："架构和数据方案里有没有你觉得不落地或者违反公司标准的？"

P3 · 你自家开发 leader——看②③④⑥。问 TA："按这个方案，你能带团队交付吗？成本估算合理吗？里程碑给的时间够吗？"

三个人都点头 → 方案可以发出去；有任意一个人皱眉 → 改到 TA 点头再发。合同前多改 3 版，胜过合同后返工 30 次。

怎么用：Token 估算公式 + 成本估算 3 步法

1
算清「单次调用 token」的构成——不是只算用户的问题！公式是：单次输入 token = 系统 prompt + few-shot 示例 + 检索出的上下文（RAG 有的话）+ 用户当次问题。单次输出 token = 模型给的回答长度。前三项是每次都花的"固定开销"，别忘。
2
用「三档规模」估月度总量——低（试点期，100 单/天）、中（推广期，1000 单/天）、高（全量，10000 单/天）。月度调用总量 = 单次 token × QPD（日均调用量）× 30 天 × (1 + 失败重试率)。失败重试率经验值 10%-20%。永远给三档，别只给一个数。
3
套价格得成本——月度成本 = 月度输入 token × 输入单价 + 月度输出 token × 输出单价。务必标注模型名和 API 版本（价格随版本变），并给两个方案对比：便宜模型 vs 强模型。政企场景还要单独列一段私有化年租费用 vs 公有云按量的对比。
4
加上「扩展性说明」——写清楚从 100 单/天扩到 10000 单/天的：① 成本会不会线性上升（一般会，加上批量优惠可能次线性）；② 是否需要升级架构（比如加缓存、切换到更便宜的模型做初筛）；③ 客户有哪些自选省钱开关（缓存开 / 关、上下文压缩、模型分级）。
5
私有化 vs 公有云对比——政企项目九成会问这个。私有化：一次性硬件 + 每年运维；公有云：按 token 计费。拐点通常在日均调用 5000-10000 之间（低于则公有云更便宜，高于则私有化摊薄成本更划算）。给客户算清拐点在哪里。

🛠️ 三、动手步骤：三个政企方案过一遍

导师说

方案文档不是背模板背出来的，是写出来的。下面三个案例，第一个我带你把六段全写一遍（脚手架级示范），第二个你自己写并给出三档成本，第三个是一份"故意有坑"的方案，你挑出问题——这是训练审查视角的最好方法。

📌 案例 A · 智能员工问答助手（跟着写完整方案）

项目背景：某集团总部人力资源部，员工 8000 人，年均政策类咨询 3 万次，HR 团队 5 人。

① 需求背景与目标

业务背景：HR 团队年均处理 3 万次政策咨询，其中 70% 是重复问题（差旅、请假、报销、股权、社保）。员工体验差（等回复 4-24 小时），HR 团队被消耗（每天 2 小时答重复问题）。

业务目标：1）政策类问题 AI 直答，员工满意度 ≥ 80%；2）HR 团队从重复问答中解放 60% 时间；3）问答准确率 ≥ 85%（有出处引用）。

② 技术方案（承接 Day 2 决策）

架构：RAG（不用 Agent 也不用工作流，纯问答场景）

组件选型：大模型选 A 家（性价比高，中文强）；向量库选 B（成熟稳定）；Embedding 选 C（支持中文长文本）。都给出备选，客户 IT 有偏好可切换。

数据流：[员工问] → [Embedding] → [向量库检索 Top5] → [LLM 生成含引用回答] → [记录审计日志]

为什么不选 Agent：制度问答需要每句可查出处，RAG 天然带引用；Agent 有幻觉风险且合规不好解释。

③ 数据方案

数据源：集团制度库现有 236 份 PDF/Word 文件，共约 120 万字。

预处理：PDF/Word 解析 → 按章节切片（500-800 字/片）→ 结构化元数据（制度编号、生效日期、适用范围）→ 生成 Embedding。

存储：向量库部署在客户内网（政企合规要求），原文件同步存客户内部文档服务器，做增量更新（季度同步）。

合规：数据不出内网，模型走客户已备案的私有化推理集群。

④ Token / 成本估算

单次调用 token 构成：

  • 系统 prompt：约 400 token（角色设定 + 输出格式规范）
  • few-shot 示例：约 500 token（2 个正确回答示例）
  • RAG 检索出的上下文：Top5 片段 × 约 600 token = 3000 token
  • 用户当次问题：平均 50 token
  • 输入合计 ≈ 3950 token
  • 输出：平均 250 token

三档规模月度成本（假设输入 0.001 元 /1K token · 输出 0.002 元 /1K token · 失败重试率 15%）：

规模日均调用月输入 token月输出 token月成本
低（试点）100约 1360 万约 86 万约 15 元
中（推广）1000约 1.36 亿约 862 万约 153 元
高（全量）3000（8000 员工按 40% 活跃）约 4.08 亿约 2586 万约 460 元 / 月

私有化 vs 公有云：本项目建议私有化推理（合规硬要求），一次性 GPU 服务器约 80 万，年运维 10 万，全量场景 3 年 TCO ≈ 110 万；公有云 3 年成本约 1.6 万——但公有云不满足数据不出内网要求，只能私有化。

⑤ 风险与替代方案

R1 · 冷门问题命中率低：制度库覆盖不到的问题（比如临时新政策），预计初期 10-15% 无法直答。替代方案：兜底转人工，同时把未命中问题月度盘点补入知识库。

R2 · 制度更新滞后：季度同步可能造成新政策 1-2 个月内答旧版。替代方案：建立"制度变更加急同步"通道，重大变更 T+1 更新。

R3 · 私有化模型能力天花板：私有化部署的模型可能比最新公有云版本落后半年。替代方案：可选混合方案，敏感问题走私有化，一般问题走公有云 API。

⑥ 里程碑与验收

M1（第 4 周）：知识库导入 + 基础问答联调；验收：50 个真实问题准确率 ≥ 80%。

M2（第 8 周）：内部试点上线（HR 部门自用）；验收：试点 2 周准确率 ≥ 85%，HR 满意度 ≥ 4/5。

M3（第 12 周）：全员开放；验收：员工满意度 ≥ 80%，HR 重复问答时间下降 ≥ 60%。

🧪 案例 B · 合同审核 Agent（自己写方案 + 三档成本）

项目背景：某央企法务中心，每月处理 800 份采购合同，重点审 5 类风险条款。要求上线一个 AI 合同审核 Agent，法务预审通过率提升到 85%。

重点练：① 六段结构别漏；② Token 估算三档：100 单/天 / 1000 单/天 / 10000 单/天，注意 Agent 场景的多轮调用要算进去。

查看参考答案

关键考察点 1 · 架构选型（承接 Day 2）：工作流 + RAG（不是 Agent）。合同审核 SOP 清晰、需要可复盘、法务合规敏感 → 工作流更合适。若客户坚持"Agent"这个词，方案里写"我们内部实现叫工作流 + 局部 AI 节点，对客户展示为智能审核 Agent"，两边都不得罪。

关键考察点 2 · Token 估算（假设单次审核平均 3 轮调用，因为要抽条款 → 查红线 → 打分）：

  • 单次输入 token：单份合同平均 6000 字 ≈ 9000 token（合同原文）+ 系统 prompt 800 + RAG 上下文 2500 ≈ 12300 token / 次；
  • 单次输出 token：约 600 token；
  • 3 轮调用相乘：输入约 37000 token / 份，输出约 1800 token / 份。
规模日均月输入 token月输出 token月成本（同价）
低100 份/天约 1.28 亿约 621 万约 140 元
中1000 份/天约 12.8 亿约 6210 万约 1400 元
高10000 份/天约 128 亿约 6.2 亿约 1.4 万 / 月

关键考察点 3 · 风险章节别只写"技术风险可控"：要写"漏审风险（准确率 < 100% 是常态，兜底策略是关键条款强制人工复核）"、"误判风险（AI 判有风险但实际无，法务效率下降）"、"合规审计（AI 判断需要留全链路日志备查）"。

常见丢分点：1）没算 Agent/多轮调用的 token 倍数；2）RAG 上下文 token 忘了算；3）忘写私有化 vs 公有云对比；4）里程碑给的时间过于乐观（1 个月上线不现实，合规审批就占 3 周）。

🧪 案例 C · 找 5 个坑（挑错题）

下面是一份"故意有坑"的方案摘要节选，请找出 5 个问题：

【项目】某市医保局智能审核系统

【方案】采用 Multi-Agent 架构，5 个 Agent 分工协作，全自动审核医保报销单，替代人工审核。

【模型】使用最新最强大模型（未标注具体名称和版本）。

【成本】预计月度推理成本约 8000 元。

【风险】技术风险可控，团队经验丰富。

【里程碑】第 4 周上线全量。

试着列出你找到的坑，然后对答案。

查看参考答案（5 个坑 + 改法）

坑 1 · 政务合规踩雷：全自动审核 + 替代人工——医保是典型的"AI 只能辅助、不能决策"的强监管场景。改法：AI 做初筛提示 + 高置信度自动通过 + 中低置信度强制人工复核，明确责任在人。

坑 2 · 架构过度：一上来就 Multi-Agent——单 Agent 还没跑通就上 5 个 Agent 分工，工程复杂度爆炸。改法：一期用工作流 + 局部 AI 节点，二期视复杂度决定是否升级到 Agent，Multi-Agent 至少三期以后。

坑 3 · 模型选型不落地：只写"最新最强大模型"——没有具体模型名和 API 版本，价格算不出、开发选不了，客户 IT 认为不专业。改法：明确写模型名、版本、上下文窗口、单价，并给 2 个备选（一强一便宜）供客户选。

坑 4 · 成本估算拍脑袋：只有 8000 元一个数字——没有 token 构成、没有三档规模、没有失败重试率、没有私有化对比。政务医保场景必须私有化，8000 元的公有云估算根本不适用。改法：按低/中/高三档给月度成本，标模型和价格版本，加上私有化 3 年 TCO 对比。

坑 5 · 风险和里程碑都是废话：「风险可控 + 4 周上线」——政务医保项目合规审批就要 3-6 周，第 4 周上线不现实；风险章节没写内容等于没写。改法：里程碑至少 4 个（合规评审 → PoC → 试点 → 全量），总周期 20-24 周；风险至少写 3 类（模型效果、合规变动、成本超支）各配替代方案。

额外加分点（找到算你厉害）：整份方案没提数据方案——医保数据涉及个人隐私，脱敏方案和权限管控必须单独一段。

📝 五、5 题小测验

先自己想 20 秒再点开答案。错项解析比正确答案更值钱，每个错项后面都藏着一次真实翻车。

Q1 · 客户采购问「你这份方案里，Token 估算的月度成本是怎么算出来的？」，最专业的回答是？
  • A. "按我们过往项目经验，差不多就这个数。"
  • B. "用户问题平均 50 token × 调用量 × 输入单价，输出同理。"
  • C. "单次输入 = 系统 prompt + few-shot + RAG 上下文 + 用户问题；月度 = 单次 × QPD × 30 × (1 + 重试率)；然后套模型单价，我在附录里给了三档规模。"
  • D. "AI 成本本来就难算，我们上线后按实际扣费即可。"
✅ 答案：C

C 完整覆盖了三个关键点：单次 token 构成（不只是用户问题）+ 月度公式（含重试率）+ 三档规模。客户采购要的就是这个层次的答案，能让他给自家老板复述。

❌ 错项解析

A 是纯粹的拍脑袋——采购听完立刻警觉"这个 PM 不专业"，接下来一定会砍价。B 遗漏了系统 prompt / few-shot / RAG 上下文——这三项才是"每次都花的固定开销"，忽略它们的估算会低 3-5 倍，一年后就是账单翻车现场。D 是把责任推给客户——采购的核心工作就是提前定预算，你说"上线后按实际扣"等于拒绝配合，直接被踢出供应商名单。

Q2 · 方案文档里的「风险与替代方案」章节，下面哪种写法最专业？
  • A. "项目团队经验丰富，技术风险可控。"
  • B. "本项目无重大风险。"
  • C. "R1 · 模型准确率可能低于 90%——兜底：置信度低于阈值转人工。R2 · 数据涉隐私——兜底：全流程内网脱敏。R3 · 成本超支——兜底：启用缓存 + 上下文压缩。"
  • D. "所有风险由甲方承担。"
✅ 答案：C

C 是标准 FDE 写法——3 类真实风险 + 每类配可执行的替代方案。风险章节的本质是"提前和客户建立风险共担契约"，写清楚了以后出问题你有话说，客户也能理解。

❌ 错项解析

A 是最典型的"没写"——"经验丰富、风险可控"是套话，出问题时是"你自己扛"的自证。B 是最危险的自证——"无风险"直接把责任兜住了，模型准确率一低客户马上找你算账。D 是把客户推走——政企客户看到"风险由甲方承担"当场撤方案，你连回旋余地都没有。

Q3 · 一个 RAG 员工问答项目，日均调用 1000 次，单次输入 4000 token / 输出 250 token。假设输入 0.001 元 /1K token · 输出 0.002 元 /1K token · 失败重试率 15%。月度成本约多少？
  • A. 约 15 元
  • B. 约 150 元
  • C. 约 1500 元
  • D. 约 4500 元
✅ 答案：B

计算过程：月输入 token = 4000 × 1000 × 30 × 1.15 = 1.38 亿；月输出 token = 250 × 1000 × 30 × 1.15 = 862.5 万。成本 = 138000 × 0.001 + 8625 × 0.002 ≈ 138 + 17 ≈ 155 元。约 150 元档。

❌ 错项解析

A 少了一个量级——很可能忘了 × 30 天，或者把输入单价当作 0.0001 算了。C 多了一个量级——常见错误是把 token 数当成"元"直接乘，忘了 /1K 的换算。D 是把输入输出单价搞反——用 0.002 算输入、0.001 算输出反了；虽然只差 3 倍，但方向性错误说明公式没吃透。

Q4 · 政企客户 IT 部说「你们方案里的私有化 vs 公有云对比，什么时候私有化划算？」，最合理的回答框架是？
  • A. "私有化肯定比公有云安全，建议直接私有化。"
  • B. "公有云按 token 付费，用多了就贵；私有化一次性投入 GPU + 运维，摊到 3 年 TCO，日均调用超过 5000-10000 次时私有化更划算——我们方案里给您画了拐点图。"
  • C. "公有云便宜，先用公有云。"
  • D. "私有化贵，别考虑。"
✅ 答案：B

B 是最专业的回答——给出计算逻辑（TCO 摊薄）+ 拐点区间 + 承诺方案里配图。政企 IT 最吃这套"给我拐点，我自己判"的回答，因为他们不想被 PM 牵着走。

❌ 错项解析

A 错在把"安全"和"划算"混为一谈——安全 = 合规角度，划算 = 成本角度，两码事。而且"肯定"这种绝对话在客户 IT 面前会被追问到破。C 是懒惰答案——"先用公有云"没回答"什么时候私有化更划算"，等于没答。D 是主观拒绝——政企场景很多合规硬要求私有化，你直接说"别考虑"等于砍掉了自己的可选方案空间。

Q5 · 综合题——客户业务方和客户 IT 方对方案争议：业务方要「4 周上线」，IT 方要「至少 12 周合规评审+PoC」，你作为 FDE 怎么处理里程碑章节？

给出你的方案文档里程碑设计和沟通话术。

✅ 参考答案：分层里程碑 + 「早交付、晚全量」策略

核心思路：把"上线"拆成三层——业务方要的"能看到"和 IT 方要的"能上生产"是两回事。给客户 IT 应有的合规和 PoC 时间，同时给业务方早期可见的价值节点。

里程碑设计：

  • M1（第 3 周） · Demo 可看：内部沙箱环境跑通主流程，业务方可现场看效果。验收：核心场景演示通过。
  • M2（第 6 周） · 合规评审完成：IT 部提出的数据脱敏 / 权限 / 日志方案通过内部合规审。验收：拿到合规部盖章。
  • M3（第 10 周） · PoC 上线：选一个部门试点，真实用户跑 2 周。验收：准确率 ≥ 目标值，用户满意度 ≥ 4/5。
  • M4（第 14 周） · 全量上线：全公司开放。验收：稳定性 SLA 达标 · 关键指标兑现。

对业务方话术："我们 3 周就能给您看到 Demo，比 4 周还早——但要真正上生产得让 IT 合规评审跑完，否则数据一出问题就是一票否决。您先看 Demo 早点确认方向，我们边合规边优化。"

对 IT 方话术："合规评审的 6 周我们完全按您的流程走，PoC 阶段我们只在您指定范围内跑，全量上线一定在合规通过之后。"

面试金句预埋："AI 方案的里程碑不是一条直线，是一颗有分层的树——业务方的可见节点和 IT 方的合规节点要分开设计，早交付价值感、晚交付稳定性。"

💼 六、面试金句预埋

文档双通视角 "AI 项目方案文档必须一份文档过三关——客户业务方看背景和验收，客户 IT 看架构和合规，采购看成本。缺一段都会有一方不认账。我写方案会先在心里列这三拨人，六段谁看哪段，写完让三拨人各自审一遍。"
成本估算文化 "Token 估算不是数学题，是采购谈判的筹码。永远给三档规模（低 / 中 / 高），标清模型和版本，算清系统 prompt 和 RAG 上下文这些'固定开销'——一年后账单不翻车的方案，第一版就已经把这些写死了。"
可演化的方案 "好的 AI 方案要让客户自己看得懂扩容路径——从 100 单/天到 10000 单/天，成本怎么变、要不要升级架构、缓存怎么开。我把这三个变量做成开关列在方案里，客户就有掌控感，也就不会砍你的价。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. 决定签合同的不是①②③（漂亮部分），是④⑤（成本 + 风险）—— 客户的采购和 PMO 才是签字人，他们只看账本和责任。（漂亮 PPT 不签合同，账本清晰才签合同。）

2. Token 估算里最大的坑是「固定开销」——系统 prompt / few-shot / RAG 上下文这三项每次都花，忘算就估低 3-5 倍。（用户问 50 token，你以为 50 token，其实每次都是 4000+。）

3. 风险章节写"风险可控"等于给自己挖坑——写清 3 类真实风险 + 3 个可执行兜底方案，出问题时才是你的护身符。（风险不是坏话，是责任边界。）
