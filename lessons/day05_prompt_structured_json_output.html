📖 二、核心讲解

是什么：让 LLM 稳定输出 JSON 的两个流派

大白话——现在业界让模型吐 JSON 有两条路：

流派核心做法一句话对比
① Prompt 引导在 Prompt 里"说服"模型输出 JSON：给 Schema、给示例、加强调通用、灵活，任何模型都能用；但稳定性靠 Prompt 功力
② response_format 强制API 参数 response_format={"type":"json_object"}，平台层面强制稳定性接近 100%，但只有部分模型支持（qwen-plus 及以上、GPT-4o 等）

实战建议：两个一起上。Prompt 里把 Schema 和示例写清楚，同时开启 response_format。这是把稳定性从 90% 提到 99% 的关键。

□ □ □ 稳定 JSON 四段口诀 □ □ □
Schema · 示例 · 校验 · 兜底
写清结构 · 给个样本 · 代码验证 · 崩了不塌房

为什么：JSON 输出的三个大坑

🚨 坑 1 · 只写"请返回 JSON"就期待稳定

你写 "请返回 JSON 格式" 的 Prompt，跑 100 次可能 60 次是干净的 JSON，剩下 40 次长这样：

好的，根据您的合同文本，我为您生成 JSON：

```json
{"甲方": "XX 公司", ...}
```

希望对您有帮助，如有问题请随时联系。

模型天生爱"包装解释"——礼貌习惯、Markdown 代码块、前后寒暄。你的 json.loads() 直接崩。

正确姿势：Prompt 结尾加一句"只输出 JSON，不要 markdown 代码块，不要任何解释文字"，再配 few-shot 示例，稳定性立刻从 60% 到 90%。

🚨 坑 2 · Schema 写得太复杂，模型直接崩

见过一个案例——PM 让模型输出这样的结构：

{
  "合同": {
    "主体": {
      "甲方": {"公司": {"名称": "", "统一社会信用代码": ""},
              "法人": {"姓名": "", "身份证": ""}},
      "乙方": {同样嵌套 4 层}
    }
  }
}

4 层嵌套 + 20 多个字段，模型每次输出都有 5-8 处结构错乱：括号不匹配、字段拼错、类型混乱。模型不是不能干，是你给它挖了太深的坑。

正确姿势：Schema 尽量扁平化到 2 层以内；复杂结构拆成多次调用（先抽 outline，再单独调用生成 detail）。

🚨 坑 3 · 没有代码校验兜底，拿到就用

模型 100 次里终究会有 1-2 次抽风——比如把金额 "800万" 输出成字符串而不是数字，把日期 "2025-01-15" 输出成 "2025年1月15日"。你后面的代码result["金额"] + 100 或 datetime.parse() 直接抛异常。

生产环境的核心原则：永远不要相信 LLM 的输出直接可用。校验 + 兜底是标配。

正确姿势：用 Pydantic 定义数据模型（自带类型校验、必填、枚举、范围），拿到 LLM 输出先 Model.parse_raw()，失败就重试或走人工兜底。

🧭 PM 行动指南：JSON 稳定 4 段策略（缺一不可）

段 1 · 明确 Schema：在 Prompt 里画出目标 JSON 的字段、类型、必填与否，写成一段 skeleton。

段 2 · 提供示例：给 1-2 个 few-shot 完整示例，模型看着葫芦画瓢，稳定性大幅提升。

段 3 · response_format 强制：API 层面开 {"type":"json_object"}——模型的输出必是合法 JSON。

段 4 · 代码兜底：Pydantic 校验类型、重试机制、失败降级到人工。四段全上，稳定性 99%+。

怎么用：5 种常见错法的诊断与修复

❌ 错法 1 · 模型多返回一段解释文字

症状："好的，为您生成如下 JSON：{...}希望有帮助。"

修复：
① Prompt 末尾加狠话："只输出 JSON 对象本身，不要 markdown 代码块（```），不要任何前置说明或后置总结，第一个字符必须是 {。"
② 加 2 个 few-shot 示例（用 user/assistant 对话）——模型模仿力比记忆力强。

❌ 错法 2 · 引号、结构错乱（JSON parse 失败）

症状：模型输出 {"name": "张三", "age": 30,}（多余逗号）或 {'name': '张三'}（单引号）。

修复：
① 上 response_format={"type":"json_object"}——阿里云百炼 qwen-plus 及以上支持，几乎解决所有语法问题。
② 代码层 try/except 兜底，parse 失败就重试或让模型 self-correct。

❌ 错法 3 · 嵌套结构频繁崩

症状：3-4 层嵌套的 Schema，每次输出都有字段位置错、层级错。

修复：
① Schema 分层设计——先让模型输出 outline（如"包含哪几节"），再对每一节单独调用生成 detail。
② 扁平化——把 合同.主体.甲方.公司.名称 展开成 甲方公司名称，一层解决。

❌ 错法 4 · 数值/字符串类型混乱

症状：金额 "800万" 而不是 8000000；日期 "2025年1月15日" 而不是 "2025-01-15"。

修复：
① Prompt 里明确类型："金额字段必须是数字（人民币元），签约日期字段格式必须是 YYYY-MM-DD"。
② 用 Pydantic 定义类型（amount: int、sign_date: date），parse 失败自动触发重试。

❌ 错法 5 · 长文本被截断，JSON 不闭合

症状：输出最后一行是 "key_terms": ["条款 1", "条款 2——模型没说完就断了。

修复：
① 检查 finish_reason——是 length 就调大 max_tokens（1500 → 3000）。
② 如果 JSON 天然大，改成"多次调用分段返回"（先返回字段列表，再一次一个字段填内容）。

# contract_extractor_v3.py
import os, json
from datetime import date
from typing import Optional
from dotenv import load_dotenv
from openai import OpenAI
from pydantic import BaseModel, Field, ValidationError

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

# 【防线 1 · Pydantic Schema】定义严格的数据契约
class ContractInfo(BaseModel):
    party_a: str = Field(description="甲方全称")
    party_b: str = Field(description="乙方全称")
    amount_cny: Optional[int] = Field(description="金额（元），未找到填 null")
    sign_date: Optional[date] = Field(description="签约日期 YYYY-MM-DD")
    duration_months: Optional[int] = Field(description="履约期（月），未找到填 null")

SYSTEM = """你是合同信息抽取助手。严格按 Schema 抽取，未找到的字段填 null，绝不编造。

【Schema】
""" + json.dumps(ContractInfo.model_json_schema(), ensure_ascii=False, indent=2) + """

【硬约束】
- 只输出 JSON 对象；第一个字符必须是 {
- 金额必须是纯数字（元），如"800 万"→ 8000000
- 日期必须是 YYYY-MM-DD 格式
- 不要 markdown、不要解释"""

def extract(contract_text: str, max_retry: int = 2) -> Optional[ContractInfo]:
    """抽取 + 校验 + 重试"""
    for attempt in range(max_retry + 1):
        try:
            resp = client.chat.completions.create(
                model="qwen-plus",
                messages=[
                    {"role": "system", "content": SYSTEM},
                    {"role": "user", "content": contract_text},
                ],
                temperature=0.1,     # 【关键】抽取任务用最低温
                # 【防线 2 · response_format 强制 JSON】
                response_format={"type": "json_object"},
            )
            raw = resp.choices[0].message.content

            # 【防线 3 · Pydantic 校验兜底】
            return ContractInfo.model_validate_json(raw)

        except ValidationError as e:
            print(f"[第 {attempt+1} 次校验失败] {e.errors()[:1]}")
            if attempt == max_retry:
                # 校验彻底失败：降级到人工
                return None
        except json.JSONDecodeError as e:
            print(f"[第 {attempt+1} 次 JSON parse 失败] {e}")
            if attempt == max_retry:
                return None
    return None

if __name__ == "__main__":
    sample = open("contract.txt", encoding="utf-8").read()
    info = extract(sample)
    if info:
        print(info.model_dump_json(indent=2, ensure_ascii=False))
    else:
        print("⚠️ 抽取失败，请人工复核")

🧪 案例 B · 自练 1：从会议纪要抽取决议 / 责任人 / deadline

需求：政企常见——一段 300-500 字的会议纪要，抽取所有"决议事项"，每条包含 内容、责任人、deadline、优先级(高/中/低)。

提示：

  1. Schema 是"列表 + 对象"（{"decisions": [{...}, {...}]}），别嵌太深；
  2. 用 Pydantic Literal["高","中","低"] 强制枚举；
  3. 责任人可能是"张总"这样的模糊称呼——Prompt 里说清楚"按原文保留，不要脑补真名"；
  4. deadline 强制 YYYY-MM-DD；模型看到"下周三"要转成具体日期还是保留原文？——你决定，Prompt 里写清楚。
查看参考实现 
from typing import List, Literal, Optional
from pydantic import BaseModel

class Decision(BaseModel):
    content: str                                # 决议内容
    owner: str                                  # 责任人（原文保留）
    deadline: Optional[str]                     # 保留原文表述，如"下周三"、"2025-06-30"
    priority: Literal["高", "中", "低"]         # 强制枚举

class MeetingResult(BaseModel):
    decisions: List[Decision]

SYSTEM = """你是会议纪要分析助手。
从纪要中抽取所有决议事项，每条包含：内容、责任人、deadline、优先级。
- 责任人按原文保留（如"张总"），不要脑补真名
- deadline 保留原文表述
- priority 只能是"高"/"中"/"低"，根据紧急程度和影响面判断
- 无决议时返回 {"decisions": []}
- 只输出 JSON 对象"""

关键点：用 Literal 卡死枚举值，模型只能选 3 个之一；空结果显式返回 [] 而不是空对象。

请你诊断：3 层问题分别是什么？怎么修？

查看参考答案

问题 1 · 模型层：Prompt 没说"只输出 JSON、不要 markdown、不要解释"，模型经常包一层 ```json 或加解释文字 → json.loads() 挂。修复：加硬约束 + few-shot。

问题 2 · Schema 层：所有字段都是空字符串 ""——模型不知道类型是啥。"天数" 有时是 3（数字）有时是 "3天"（字符串），后面 +1 直接崩。修复：Schema 明确类型，"天数" 标注 number；上 Pydantic days: float。

问题 3 · 代码层：没有 try/except、没有 response_format、没有重试。20% 失败率里有很大一块是本可以自动恢复的。修复：加 response_format={"type":"json_object"}、Pydantic 校验、失败重试 2 次、彻底失败降级到人工。

合计修复后：失败率从 20% 降到 <1%。这就是"三层防线"的完整威力。

📝 五、5 题小测验

建议先想 30 秒再翻答案。错项解析才是这一节的核心资产。

Q1 · 你的 JSON 输出经常被模型包一层 ```json\n{...}\n``` markdown，最合理的一线修复是？
  • A. 让开发同学在代码里用正则清洗
  • B. Prompt 里加"只输出 JSON 对象本身，不要 markdown 代码块，第一个字符必须是 {"，并开启 response_format
  • C. 换个更贵的模型（qwen-max 就不会犯这种低级错）
  • D. 忽略这个问题，反正代码总能跑通
✅ 答案：B

这是标准的"模型层+平台层"双管齐下：Prompt 明说不要 markdown + response_format 强制 JSON。这是 FDE 面对稳定性问题的第一反应——在信息源头治理，而不是在数据流末端擦屁股。

❌ 错项解析

A 是"补救思维"——正则清洗只能兜底，不能替代源头治理，模型下次换个错法你还得再写正则。C 错在把问题甩给成本——qwen-max 更贵但同样会犯 markdown 包装的错，不是模型档次问题。D 是不专业——生产环境 5% 的失败率乘以每天 10000 次调用就是每天 500 次崩溃。

Q2 · 稳定 JSON 四段口诀是什么？
  • A. 温度 · 长度 · 重试 · 缓存
  • B. Schema · 示例 · 校验 · 兜底
  • C. 输入 · 输出 · 校验 · 部署
  • D. Prompt · 模型 · 参数 · 结果
✅ 答案：B

Schema 定结构 → 示例给样本 → 校验守类型 → 兜底防崩塌。这四段对应了"模型看得懂"、"模型学得会"、"代码验得住"、"崩了不塌房"四个维度。

❌ 错项解析

A 混淆了参数调优和结构化输出——温度、重试是通用技术，不是 JSON 稳定的专属方法。C 太笼统——"输入·输出"不是可执行的策略，只是流程节点。D 是四大要素而非四段方法论——每个 LLM 应用都有这四要素，不专门解决 JSON 稳定问题。

Q3 · 你的合同抽取器要求"金额必须是数字（元）"，但模型偶尔返回 "800万"，最合适的修复姿势？
  • A. Prompt 里加"金额必须转成纯数字（元），如'800万'→8000000"，同时用 Pydantic amount: int 校验
  • B. 只加 Prompt 说明就够了，Pydantic 太重
  • C. 在业务代码里写一堆 if-else 把"800万"转成 8000000
  • D. 换更强的模型 qwen-max
✅ 答案：A

这就是三层防线的典型体现——Prompt 说清楚（模型层）+ Pydantic 强类型（代码层）双重保险。Prompt 让模型 90% 时候做对，Pydantic 让剩下 10% 抽风的输出自动触发重试或降级。

❌ 错项解析

B 少了兜底——模型永远有几率抽风，没 Pydantic 校验意味着抽风的输出会直接流入下游业务，崩得更远。C 是把 LLM 稳定性问题转嫁给业务代码——每接入一个新格式就要改代码，维护地狱。D 是花钱解决勤奋——qwen-max 也会犯这种错，问题在于没建校验兜底体系。

Q4 · 下列哪个 Schema 设计最容易让模型崩？
  • A. 扁平的 5 个字段：{party_a, party_b, amount, date, duration}
  • B. 一层列表：{decisions: [{content, owner, deadline}, ...]}
  • C. 4 层嵌套：{合同:{主体:{甲方:{公司:{名称,代码}}}}}
  • D. 带枚举：{priority: "高"|"中"|"低"}
✅ 答案：C

嵌套 4 层是模型的噩梦——括号平衡、字段位置、层级顺序，每一次输出都有多个可能出错的点。经验值：Schema 尽量扁平化到 2 层以内，超过就拆多次调用。

❌ 错项解析

A 是最稳定的形态——扁平结构，模型正确率最高。B 一层列表模型完全能搞定——few-shot 一次示例即可稳定。D 枚举反而提升稳定性——限定选项后模型不会瞎写，Pydantic Literal 还能校验。

Q5 · 综合题——生产环境 Agent 一天调用 10 万次，JSON 稳定率要求 99.9%，你怎么设计？

简答题，写出你的四段策略。

✅ 参考答案

段 1 · 模型层：Prompt 里完整 Schema + 2-3 个 few-shot + 硬约束（不要 markdown / 只输出 JSON / 字段类型强调 / 未知填 null 不编造）。

段 2 · 平台层：response_format={"type":"json_object"}；temperature=0.1；max_tokens 留 30% 冗余；每次检查 finish_reason。

段 3 · 代码层：Pydantic 严格模型定义（类型/必填/枚举/范围/正则）；parse 失败自动重试 2 次（第二次可把"上次错在哪"塞回 Prompt 让 self-correct）；仍失败降级到人工队列。

段 4 · 可观测层：把每次 JSON 校验失败、finish_reason=length、重试次数都打到监控——PM 视角看板必备。JSON 稳定率是生产 Agent 的核心 KPI。

面试金句预埋："稳定 JSON 从来不是一层能解决的问题——模型层 + 平台层 + 代码层 + 可观测层，一层都不能少。"

💼 六、面试金句预埋

稳定性至上 · 三层防线 "让 LLM 稳定输出 JSON 从来不是一层能解决的问题。我的做法是三层防线——模型层 Prompt 写清 Schema 和 few-shot，平台层用 response_format 强制，代码层用 Pydantic 校验兜底加重试。三层全上，稳定率从 60% 干到 99% 以上。"
Schema 优先 · 契约思维 "我把 LLM 的输出当成接口契约来管——Schema 就是 API 定义。字段类型、必填、枚举、范围都要写死，模型只是这个契约的一个实现方。契约稳了，业务代码就稳，客户才敢真上线。"
代码兜底文化 · 永远不信任 LLM "我给团队立的规矩——永远不要相信 LLM 的输出直接可用。哪怕它 999 次都对，那第 1000 次抽风就能让整个系统崩。Pydantic 校验、失败重试、人工降级是标配。这不是不信任 AI，这是工程负责。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. "请返回 JSON"这五个字的稳定率只有 60%——Prompt 工程从这里才真正开始。（PM 常见误区：以为写清楚就够了，其实模型比你想的会走神。）

2. Schema 不是越详细越好——层级超过 2 层就要拆。（工程直觉：模型和你一样，看深度嵌套的东西也会晕。）

3. 生产环境不看单次成功率，看的是 99.9% 稳定率下的 P99 延迟。（管理直觉：从"能跑"到"能生产"之间的差距，就是一个 FDE 的价值。）
