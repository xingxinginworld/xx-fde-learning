🎯 一、今日目标

导师说

你在某公司干过这么多年某单位项目，日志你不是没读过——Nginx access log、Tomcat catalina.out、Java 堆栈异常你都会翻。但 AI 应用的日志跟传统 Java 系统完全不是一个东西。传统日志你看到 NullPointerException，定位到某一行代码就完事了；AI 应用你看到 "答错了"，可能是 Prompt 写得不对、可能是检索没召回、可能是模型幻觉、可能是工具返回值格式变了——五层里任何一层出问题都长一个样：输出不对。

这就是为什么 AI debug 比传统难 10 倍。今天补的就是这个能力——你要能把"输出不对"这一句话，拆成 5 个可查的点，逐层追下来。这就是 FDE 和普通 PM 拉开差距的第一个技术分野。

  • 理解 「AI 应用可观测性三件套」——Logs / Traces / Metrics 分别看什么
  • 掌握 「采分因改验」5 步 Bad Case 分析法，30 分钟定位一个真实 case
  • 会用 Langfuse（或 LangSmith）读一条 Trace，知道每一环出了啥事
  • 能建 Bad Case 库——不是每次都从零开始查，而是查过一次终身受益
  • 能对领导说出 「这个 case 我用了 A/B 测试对比了 3 版 Prompt」 的话术

📖 二、核心讲解

是什么：AI 应用可观测性三件套

可观测性（Observability）这个词你在运维那边听过，但在 AI 场景下它长得不一样。传统运维看的是"机器活没活、接口通没通"；AI 应用看的是"模型在想什么、每一环拿到了什么、最终为什么输出这个"。

类别记录什么用来回答的问题典型工具
Logs 日志每一次调用的 input / prompt / output / usage / latency / error"这一条请求发生了什么？"ELK / Loki / 自建 JSON 落盘
Traces 链路一次会话/一次 Agent 运行里，各步骤的调用树、耗时、上下文流转"多步链路里哪一步出错？"Langfuse / LangSmith / Phoenix
Metrics 指标调用量、Token 消耗、平均延迟、错误率、命中率、幻觉率"整体健康度怎么样？趋势是好是坏？"Prometheus + Grafana / Langfuse Dashboard

反直觉的地方：很多团队以为"打日志就够了"——错。没有 Trace，多步 Agent 链路你根本看不出问题在哪一步；没有 Metrics，你不知道昨天准确率是不是悄悄掉了 5 个点。三件套要一起上。

为什么：AI debug 的三个大坑

🚨 坑 1 · 出问题就重跑一遍看能不能复现

传统 Java bug 你重跑一遍能复现，就能 debug。AI 应用你重跑，因为 temperature > 0，输出就是不一样——你以为"这次好了"，实际上是换个用户问法一模一样的 bug 又出来了。

不确定性系统这样调试等于自杀。正确姿势是：把出问题那一条完整的 input / prompt / context / output 全存下来，回到评测集里反复分析，而不是重跑。

PM 视角提醒：客户投诉一个 Bad Case，你的第一句话不是"我再试试看"，是"能把当时的问题原话和时间点给我吗，我拉日志"。

🚨 坑 2 · 只看输出不看中间步骤

用户问"招标截止时间"，Agent 回答"投标截止时间是 X 月 X 日"。只看输出你会以为是模型幻觉、想换个模型；打开 Trace 才发现，其实是检索环节 top-3 里全是"投标"相关的 chunk，"招标"这个词的 chunk 排到了 top-8——模型基于给它的上下文答得没毛病，问题在检索，不在生成。

RAG / Agent 里到底哪一步出错，只看输出完全黑盒。必须打开链路看每一步的 input/output。

🚨 坑 3 · 没有 Bad Case 库，每次都从零开始查

今天客户报了一个 case，你花 2 小时定位到"检索问题"，改了 Prompt 上线。三周后 另一个客户报了个几乎一样的 case——你已经忘了当时怎么定位的，又花 2 小时。半年后再来一个，还是 2 小时。

问题不在你记性差，在你没有 Bad Case 库。每个 case 应该沉淀成一条记录：现象 / 定位过程 / 根因 / 改进方案 / 是否已进回归集。这是 FDE 团队最值钱的资产之一。

老外包 PM 的痛点：你以前做交付，"文档"是甩给客户的东西，自己不留。做 FDE 反过来——Bad Case 库是给自己留的，客户可能永远看不到，但它决定了你团队的迭代速度。

🧭 PM 行动指南：可观测性建设的 3 层门槛

Layer 1 · 最低门槛（第 1 周就要有）：每次 LLM 调用都记 input + prompt + output + model + usage(token) + latency + timestamp + user_id——JSON 落盘或 MongoDB 存都行，先把数据攒起来。

Layer 2 · 进阶（PoC 结束前要有）：接入 Langfuse / LangSmith，拿到多步 Trace 视图。Agent 多步调用、RAG 多环节都能看到全链路耗时和内容。

Layer 3 · 成熟（正式交付要有）：加上 Metrics Dashboard——每日调用量、Token 消耗曲线、平均延迟、错误率、Bad Case 命中回归集比例、幻觉率抽检值。这一层是给运营和客户看的，不是给自己查 bug 用的。

怎么用：Bad Case 分析 5 步法

1
采集——日志埋点 + Trace 平台。推荐 Langfuse（开源、可自部署，政企环境友好，比 LangSmith 更适合国内合规）。埋点最低要求：input / prompt(完整拼接后的) / retrieval 结果 / tool 调用 / output / latency / cost。埋点写代码里的时候用 decorator 或 middleware，别散在业务代码里。
2
分类——把 Bad Case 归入 5 大类：① 幻觉（编造）② 检索漏召回 ③ 工具调用错误 ④ 格式崩坏 ⑤ 超时/异常。归类不是精确科学，凭第一直觉分即可，分错了后续再改。分类的价值是让你能按类型统计——如果 60% 都是"检索漏召回"，那你 Prompt 调再多都是白搭，该动 RAG 的切分和向量化了。
3
归因——定位到具体环节。这一步靠 Trace 视图。看：Prompt 里有没有相关信息？检索 top-k 命中没命中？工具返回值格式对不对？模型输出是否严格 follow Prompt 里的格式要求？归因不清就别急着改，宁可多花 20 分钟找准，也别盲改一小时白干。
4
改进——先小改再大改。三种改法优先级：Prompt 微调（最便宜）→ 检索/工具/参数调整（中等）→ 换模型/加微调（最贵）。每次改动必须 A/B 测试对比——拿 20-50 条评测集跑一遍新旧两版，看命中率变化，别只看那一条 Bad Case 好没好。灰度上线：先 5% 流量试，再 30%，再全量。
5
验证——把这条 Bad Case 加入回归测试集。这一步 80% 的团队都跳过——修完就上线，下次改另一个 Bad Case 时把这条又改坏了都没人知道。回归集是你的护城河，每一条 Bad Case 都是一块砖。回归集要能一键跑，跑完出报告：本次改动让整体命中率从 X% 到 Y%，其中 3 条历史 Bad Case 有 1 条又崩了。

🛠️ 三、动手步骤：跟着做一个真实 Bad Case 全过程

导师说

下面这个 case 是某单位某供电公司招投标 RAG 助手的真实 Bad Case，脱敏后拿来给你练。跟做完你就掌握了从"发现问题"到"回归验证"的完整闭环。后两个自己练。

📌 案例 A · RAG 答错"招标截止时间"（跟着做）
现象

用户问："2024 年新一代智能配电终端项目的招标截止时间是什么时候？"

Agent 答："投标截止时间是 2024 年 3 月 15 日 17:00。"

——听起来好像挺专业，但用户炸了："我问的是招标截止时间，不是投标截止时间！这两个是完全不同的日期！"

Step 1 · 采集：捞出这条完整 Trace

打开 Langfuse，按 user_id + timestamp 定位到这条会话。Trace 视图显示这次调用有 3 个 span：retrieval（检索）→ rerank（重排）→ generation（生成）。全部展开看。

Trace ID: trace-abc123 ├─ retrieval (312ms) │ Query: "招标截止时间" │ Top-5 chunks retrieved: │ #1 score=0.87 "...投标文件递交截止时间：2024年3月15日..." │ #2 score=0.85 "...投标保证金缴纳截止：2024年3月10日..." │ #3 score=0.83 "...投标澄清答疑截止：2024年3月8日..." │ #4 score=0.79 "...招标公告发布日期：2024年2月20日..." │ #5 score=0.76 "...招标文件领取截止：2024年2月28日..." ├─ rerank (48ms) → 保留 top-3（都是"投标"） └─ generation (1.2s) Prompt片段: "基于以下资料回答问题：[chunk1, chunk2, chunk3]..." Output: "投标截止时间是 2024 年 3 月 15 日 17:00。"
Step 2 · 分类

属于哪一类？——不是幻觉（答案确实在资料里），不是格式崩，不是超时。是"检索漏召回"——用户问"招标截止"，top-3 全被"投标"相关内容占了，"招标文件领取截止"排到 top-5 才出现，重排后被砍掉。

Step 3 · 归因

为什么会漏召回？三个可能：

  • ① 向量模型对"招标 vs 投标"的语义区分不够（这两个词向量太接近）
  • ② 切片时"招标"相关内容的 chunk 数远少于"投标"相关（数据分布不均）
  • ③ 检索没做 query 扩展/关键词过滤（"招标"这个关键词权重不够）

翻底层数据验证——发现问题主要是 ①+③："招标"和"投标"在通用中文向量模型里余弦相似度高达 0.94，模型觉得这俩差不多。而 top-5 里 4 条都是"投标"，只有 1 条是"招标"相关。

Step 4 · 改进：三版方案 A/B 对比
方案改动评测集命中率成本
V0原始（纯向量检索）62%（50 条评测集）基线
V1Prompt 里加"注意区分'招标'和'投标'是两个不同概念"68%（+6pp）免费，见效小
V2检索加入 BM25 关键词分数 × 0.4 + 向量分数 × 0.6 混合排序84%（+22pp）改代码，见效显著
V3V2 + 增加 query 扩展（"招标截止" → "招标文件领取截止 / 招标截止日期"）91%（+29pp）再加一层，工程量中

决策：V2 上线（性价比最高），V3 加入 Roadmap 下个迭代做。灰度：5% 试 3 天 → 30% 试 1 周 → 100%。

Step 5 · 验证：加入回归集

把这条 case 连同"招标 vs 投标"整个语义对，扩展成 8 条回归测试用例（不同表述、不同项目、不同时间点），一起进回归集。以后每次改 RAG / 换向量模型 / 调 chunk 大小，都要跑这 8 条 + 原有回归集，命中率不能低于 90%。

📓 复盘一句话

不是模型不行，是检索不行。80% 的 RAG Bad Case 都在检索环节，不在生成环节。

🧪 案例 B · Function Calling 幻觉（自己练）

现象：用户问"帮我查一下某单位某分公司 2024 年 Q3 的项目中标数量"。Agent 调用了 query_bid_stats(company, year, quarter) 工具，但工具返回值是 {"error": "no data for 2024Q3"}。结果 Agent 最终答："某单位某分公司 2024 年 Q3 共中标 47 个项目。"

按 5 步法自己走一遍，找出这是哪一类 Bad Case、归因到哪一环、你的改进方案是什么。

查看参考答案

分类：③ 工具调用错误 + ① 幻觉（组合型）。工具返回了 error，但模型无视 error，编造了数字。

归因：Prompt 里没有告诉模型"工具返回 error 时该怎么办"。模型的默认行为是"编一个合理的数字应付用户"——这是模型的老毛病。

改进方案（3 层）：

  1. Prompt 硬约束：加一段"如果工具返回 error 字段，你必须直接把 error 告诉用户，禁止编造数字"。这一步能拦住 70% 的幻觉。
  2. 代码兜底：在工具调用返回后加一个中间层——如果 error 存在，直接跳过模型生成，用固定话术回复"该数据暂不可查询，可能原因：XX"。这是最稳的。
  3. Trace 打标：把所有"工具返回 error 但模型没提 error"的 case 打标签自动落到 Bad Case 库，人工不用一条条捞。

验证：加 15 条工具异常回归用例（超时/error/空数据/字段缺失），每次改动都跑。

面试金句："Function Calling 里模型忽视工具异常继续编答案，是 Agent 里最隐蔽的幻觉。Prompt 拦一层 + 代码兜一层，两条都不能少。"

🧪 案例 C · 判断题——给一段日志，问题在哪一层？（自己练）

场景：你收到用户反馈"Agent 答非所问"。捞出的 Trace 如下：

用户 Query: "帮我把上个月的报销单汇总成 Excel" ├─ intent_router (85ms) │ 分类结果: "数据查询意图" (置信度 0.71) ├─ retrieval (220ms) │ Query: "上个月的报销单" │ Top-3: 都是"报销制度说明"chunk ├─ generation (900ms) │ Output: "根据公司报销制度，员工报销需要..."

问题出在哪一层？① 意图识别？② 检索？③ 生成？给出你的判断和归因。

查看参考答案

问题在①意图识别层——用户的真实意图是"生成 Excel 报表"（工具调用类），但意图路由把它分成了"数据查询"（RAG 类），置信度只有 0.71 也偏低。分错了意图，后面走了 RAG 分支，检索的都是"报销制度"，跟用户想要的差了十万八千里。

归因确认方法：如果这里意图判对了走"工具调用"分支，应该调用 generate_expense_report(month)，才是用户要的。所以后两层不是问题源头，只是被前面带偏了。

改进方案：① 意图分类器加 few-shot（把"汇总/生成/整理成 Excel"这类模式喂进去）；② 意图置信度低于 0.8 时反问用户"您是想查询报销数据还是生成报销汇总表？"——反问澄清比乱猜好 10 倍。

关键学习点：多环节 Agent，先看第一环，第一环错了后面全错。Trace 从上往下看，别从输出倒推。

📝 五、5 题小测验

建议先自己想 20 秒再点开答案。错项解析比正确答案更值钱。

Q1 · 用户反馈一个 Bad Case，你的第一反应最该是？
  • A. 让用户重问一次，看能不能复现
  • B. 直接改 Prompt 试试看能不能好
  • C. 拉这条会话的完整 Trace 日志，看每一环发生了什么
  • D. 换个更贵的模型跑跑试试
✅ 答案：C

Bad Case 分析 5 步的第一步就是"采集"——拉完整 Trace 才有分析基础。没有数据的调优就是碰运气。

❌ 错项解析

A 是"坑 1"——AI 是不确定性系统，重跑很可能"这次好了"，但 bug 只是被 temperature 藏起来了。B 跳过归因直接改是最典型的盲改——你都不知道问题在检索还是生成，改 Prompt 大概率白改。D 换模型是最贵最偷懒的方案——先看清问题在哪一层，很多时候换模型没用（问题在检索或工具层）。

Q2 · Logs / Traces / Metrics 三件套，下面搭配正确的是？
  • A. Logs 看趋势、Traces 看单次、Metrics 看细节
  • B. Logs 看单次调用细节、Traces 看多步链路、Metrics 看整体健康度趋势
  • C. 三者作用一样，选一个就够
  • D. Traces 是 Logs 的升级版，有 Traces 就不用 Logs 了
✅ 答案：B

Logs 回答"这一次发生了什么"（单点）、Traces 回答"链路里哪一步出错"（多步）、Metrics 回答"整体好不好、趋势对不对"（宏观）。三者互补，缺一不可。

❌ 错项解析

A 把三者的角色对调了——Logs 才是细节，Metrics 才是趋势，Traces 是链路。C 是典型误区——只有 Logs 你看不到链路，只有 Metrics 你查不到具体 case。D 错在 Traces ≠ Logs 升级版——Traces 关注"步骤之间的关系"，Logs 关注"每一步内部的内容"，一个偏拓扑一个偏内容。

Q3 · 改完 Prompt 后，验证有效性的正确方式是？
  • A. 拿出问题那一条 Bad Case 重跑，好了就上线
  • B. 拿 20-50 条评测集（含 Bad Case + 历史正常 case）跑 A/B 对比
  • C. 让客户试用一周，没投诉就算过
  • D. 相信自己的经验，Prompt 写得漂亮就没问题
✅ 答案：B

A/B 测试 + 评测集是唯一靠谱的验证方式。只看 Bad Case 那一条是"过拟合到 Bad Case"——你改的 Prompt 可能修好了这一条，但把其他 30 条本来好的答坏了。评测集必须同时覆盖 Bad Case 和历史正常 case。

❌ 错项解析

A 是最常见的错法——修好一条不代表整体好了，甚至可能整体变差。C 把生产环境当测试场，客户不投诉不代表没问题（很多用户遇到 bug 直接不用，不会来投诉）。D 是新人 FDE 最容易犯的傲慢——没数据支撑的"我觉得"在 AI 项目里等于零。

Q4 · 关于 Bad Case 库，下面说法错误的是？
  • A. 每个 Bad Case 都应该沉淀成一条记录，含现象/根因/修复方案
  • B. Bad Case 库主要给客户看，展示我们发现和修复问题的能力
  • C. 每条 Bad Case 都应该扩展成 3-5 条回归测试用例
  • D. 每次改 Prompt / 换模型都要跑一遍回归集，命中率不能倒退
✅ 答案：B

Bad Case 库主要是给自己团队用的——是内部资产、迭代护城河。客户可能永远看不到，但它决定你团队第二次遇到同类问题时是 2 分钟解决还是 2 小时解决。

❌ 错项解析

A 说的是标准做法——不沉淀就等于白查。C 说的扩展一条为多条也对——一条 Bad Case 背后往往是一类问题，只写一条测试用例覆盖不全。D 是回归测试的核心纪律——不跑回归集就上线 = 用生产环境当测试环境。

Q5 · 综合题：RAG 助手用户反馈"经常答非所问"，你会怎么系统地查？

按 5 步法给出你的排查计划。

✅ 参考答案：先分类归因，再决定改哪一层

Step 1 · 采集：从近 7 天日志中捞出所有 用户显式或隐式打差评 的会话（点踩、追问"你没答我问题"、重复提问），Trace 全部导出。目标至少 30 条。

Step 2 · 分类：按 5 大类打标签。假设结果：检索漏召回 60%、幻觉 20%、格式崩 10%、工具错 5%、其他 5%。这一步定了你后面的重心。

Step 3 · 归因：拿出"检索漏召回"那 18 条挖深——共同点是啥？可能是：切片过大导致 top-k 稀疏 / 用户 query 里的口语化词（"截止时间"vs 文档里的"申报期限"）向量匹配差 / 某个业务领域的 chunk 数量本身就少。

Step 4 · 改进：分层出手——① Prompt 加澄清反问兜底（成本最低，先做）② 检索加 BM25 + 向量混合（工程中等，做第二版）③ 领域数据补充切片和领域向量微调（成本高，看 ROI 再上）。三层各自 A/B 对比评测集。

Step 5 · 验证：把这 30 条 Bad Case 全部进回归集，扩展到 50-80 条。每周跑一次回归，命中率作为团队北极星指标之一。

面试金句："看到'经常答非所问'我不会去改 Prompt，我会先拉 30 条 Trace 分类。60% 是检索问题就动检索，60% 是幻觉才动 Prompt——用数据定位方向比经验拍脑袋靠谱 10 倍。"

💼 六、面试金句预埋

可观测性文化 "AI 应用不能没有可观测性。Logs 看单点、Traces 看链路、Metrics 看趋势，三件套缺一不可。我们团队第一周就把 Langfuse 部起来了——没这个基础后面所有 Bad Case 都是靠猜。"
Bad Case 库价值 "我最看重的团队资产不是 Prompt 库，是 Bad Case 库 + 回归测试集。每一条问题都沉淀成一块砖——半年之后新员工来查历史 case 30 分钟能上手，而不是每次都从零开始。这才是可持续的迭代能力。"
灰度纪律 "Prompt 一改就全量上线是我见过最危险的操作。我们所有改动都走 A/B + 灰度 5%→30%→100%。评测集拿命中率说话，命中率不涨 3pp 以上不上线。感觉是'好像好一点'的时候，往往就是回归又崩一条历史 case。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. AI debug 出问题不能重跑复现——不确定性系统重跑等于自杀。（用日志 + Trace 分析，别靠重现。）

2. 80% 的 RAG Bad Case 在检索层，不在生成层。（先看 Trace 里 retrieval 的 top-k，别急着骂模型。）

3. 修好一条 Bad Case 不算完事——加入回归集才算完。（没进回归集的修复，下次改动就会把它改坏。）

🎯 老 PM 转 FDE 的思维切换

你以前做交付管的是"进度、质量、验收"这三件事，出了问题找开发。现在做 FDE，"质量"这一件事有一半要你自己扛——因为 Bad Case 定位没有代码 bug 那么清楚，需要一个懂业务又能读日志的人先分类再派活。这个人就是 FDE。你的某公司多年交付经验在"分类归因"这一步是加分项——你知道客户投诉的话怎么听、真痛点在哪。
