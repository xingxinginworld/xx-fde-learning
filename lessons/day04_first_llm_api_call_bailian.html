📖 二、核心讲解

是什么：一次 LLM 调用到底发生了什么？

大白话——你调用一次 API，就是把一段文字打包成 HTTP 请求发出去，模型算完了再把答案打包成 JSON 发回来。就这么简单。之所以感觉神秘，是因为中间"模型推理"那一步在服务器里，你看不见。

┌─────────────┐ HTTP POST ┌───────────────┐ 转发 ┌──────────────┐ │ 你的代码 │ ────────────▶ │ API 网关 │ ────────▶ │ 模型推理引擎 │ │ (Python) │ 带 Key 认证 │ (dashscope) │ │ (qwen-plus) │ └─────────────┘ └───────────────┘ └──────┬───────┘ ▲ │ │ │ │ ┌───────────────┐ JSON 响应 │ └───────│ 客户端 Parse │ ◀────── (choices + usage) ◀──── ┘ └───────────────┘

把这个流程拆成 5 个动作，就是今天要记的口诀：

动作你要做什么为什么重要
① Key 拿 Key去平台申请 API_KEY，放到环境变量里没 Key 一切免谈；硬编码到代码里就是安全事故
② Endpoint 定地址选好平台 URL（百炼 / OpenAI 兼容模式）选错地址会 404；OpenAI 兼容模式代码几乎通用
③ Request 组请求拼 messages、选 model、调 temperature参数决定了输出稳定性和成本
④ Response 收响应看 content、usage、finish_reason不看 usage 你永远不知道花了多少钱
⑤ Parse 解结果取出 content，做异常处理网络抖动 / 超时 / 限流是常态，兜底必备
□ □ □ 五段调用口诀 □ □ □
Key · Endpoint · Request · Response · Parse
拿钥匙 · 定门牌 · 递话 · 收话 · 拆包

为什么：PM 上手 API 的三个大坑

🚨 坑 1 · 只在 PPT 上看过，从没自己跑过一次

这是 90% 的 PM 转 FDE 的头号病。你会画架构图、会写"调用大模型 API"这五个字，但真让你跑一次，你不知道 Key 从哪申请、依赖装哪个包、Response 长啥样。

结果就是——和客户聊方案时，你说的每一句都是二手信息。客户问"这个 Token 大概烧多少钱"，你要回去问算法同学；客户问"接口延迟能到多少"，你还要回去问。这就是外包 PM 和 FDE 的分水岭。

正确姿势：不管你多忙，先花 30 分钟把最简的 Hello World 跑通。跑一次，你以后在客户面前的底气就不一样。

🚨 坑 2 · 拿到 Response 就当结果，不看 usage 和 finish_reason

Response 里除了 content（模型说的话），还有两个 PM 必看的字段：

  • usage：这次调用烧了多少 Token（prompt_tokens + completion_tokens）——直接对应花了多少钱。
  • finish_reason：模型为什么停下来。stop 是自然结束；length 是被 max_tokens 截断（结果不完整！）；content_filter 是被安全策略拦了。

见过太多 PM 拿到一段被截断的 JSON 直接给客户演示，客户当场发现最后一行是半截——尴尬到没法收场。

正确姿势：每次调用后，先打印 usage 和 finish_reason，形成肌肉记忆。

🚨 坑 3 · 把 API Key 硬编码到代码里推到 Git

新手最贵的一课——把 api_key = "sk-xxxxxx" 直接写在代码里，然后 git push 到 GitHub。3 小时后你会收到平台账单短信：10 万 Token 一夜被刷完。

爬 GitHub 找泄漏 Key 是有专门的黑产脚本的。就算你的仓库是"私有"，团队里任何人拉一份到自己机器上都可能有风险。

正确姿势：永远用 环境变量 或 .env 文件（配套 .gitignore 把 .env 排除）读 Key，代码里只出现变量名，不出现 Key 值。

🧭 PM 行动指南：跑通第一个 API 调用要过 4 关

关 1 · Key 拿到：去阿里云百炼申请（新账号有免费额度），复制 sk- 开头那串。

关 2 · 依赖装好：pip install dashscope（官方 SDK）或 pip install openai（走百炼的 OpenAI 兼容模式，代码更通用）。

关 3 · 网络通：如果你在公司内网，先确认 dashscope.aliyuncs.com 不在防火墙黑名单里。测试：curl -I https://dashscope.aliyuncs.com 有响应就 OK。

关 4 · 响应正确：跑通后看到 choices[0].message.content 里有模型回答的中文——这一关过了，你今天的目标就达成 80%。

怎么用：5 步搭好第一个调用

1
申请 Key —— 去 bailian.console.aliyun.com 注册登录，进"API-KEY 管理"页面创建。新用户通常有百万级 Token 免费额度，够你练一整周。
2
装依赖 —— 打开终端跑 pip install openai python-dotenv。用 openai 库走 OpenAI 兼容模式，好处是以后换 DeepSeek、Kimi、豆包代码几乎不动。
3
写 Key 到 .env —— 在你的项目根目录建一个 .env 文件，写 DASHSCOPE_API_KEY=sk-xxxxxxxx。同目录建 .gitignore 加一行 .env。
4
写第一段调用代码 —— 见下面动手步骤 v1 版本，抄进 hello_llm.py，python hello_llm.py 运行。
5
看 Response、调参数 —— 跑通后先打印全部 Response 看结构，再逐步加 system_prompt、调 temperature 感受输出变化。

🛠️ 三、动手步骤：3 段代码从 Hello World 到多轮对话

导师说

下面这三段代码是递进的——v1 最简、v2 加人设、v3 加对话历史。你先原封不动跑一遍 v1，跑通了再改到 v2，v3 是给你未来做"多轮问答 Agent"的雏形。全程建议边跑边把 Response 打印出来看，比看 100 页文档管用。

📌 案例 A · 跟做：v1 最简一次调用（能跑就赢一半）
目标

让模型回答一句话："你是谁？"——看看它怎么回。

完整代码 · hello_llm_v1.py
# -*- coding: utf-8 -*-
# hello_llm_v1.py —— 你人生第一段大模型调用代码

import os                              # 用来读环境变量
from dotenv import load_dotenv         # 加载 .env 文件里的 Key
from openai import OpenAI              # OpenAI 兼容客户端

load_dotenv()                          # 把 .env 里的变量注入到 os.environ

# 【第 1 步 · Key】从环境变量读 Key，绝对不要写死在代码里
api_key = os.getenv("DASHSCOPE_API_KEY")

# 【第 2 步 · Endpoint】百炼的 OpenAI 兼容地址（记牢这个 URL）
client = OpenAI(
    api_key=api_key,
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

# 【第 3 步 · Request】组请求：messages 是对话列表，role 有 user/system/assistant
response = client.chat.completions.create(
    model="qwen-plus",                 # 用性价比款；正式项目可换 qwen-max
    messages=[
        {"role": "user", "content": "你是谁？用一句话介绍自己。"}
    ],
)

# 【第 4 步 · Response】把关键字段都打出来看一眼
print("=== 模型回答 ===")
print(response.choices[0].message.content)   # 模型说的话
print("\n=== usage（烧了多少 Token） ===")
print(response.usage)                         # 输入/输出 Token 用量
print("\n=== finish_reason（为啥停下） ===")
print(response.choices[0].finish_reason)      # stop=正常 / length=被截断
预期输出
=== 模型回答 ===
我是通义千问，由阿里云研发的大规模语言模型，可以回答问题、创作文字、编程等。

=== usage（烧了多少 Token） ===
CompletionUsage(completion_tokens=28, prompt_tokens=13, total_tokens=41)

=== finish_reason（为啥停下） ===
stop
你要看懂的 3 件事
  1. choices[0]——为啥有下标？因为一次调用可以让模型返回多个候选（n=3 就有 3 个），默认只返回 1 个，所以取 [0]。
  2. usage 三个字段——prompt_tokens 是你发过去的，completion_tokens 是模型返回的，total 是总和。钱按 total 收。
  3. finish_reason=stop——最健康的状态。如果看到 length，说明输出被 max_tokens 卡断了，要调大参数。
📌 案例 A · 跟做：v2 加 system_prompt 和 temperature
目标

让模型扮演"资深招投标顾问"，用低温度输出稳定答案。

完整代码 · hello_llm_v2.py
# -*- coding: utf-8 -*-
# hello_llm_v2.py —— 加人设 + 调参数

import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

# 【关键 1】system 消息：给模型定人设，会影响后续所有回答的风格
system_prompt = """你是一位资深招投标顾问，回答风格：
1. 先给结论，再给理由；
2. 涉及金额或期限的必须明确写数字；
3. 不确定的地方说"需要根据招标文件确认"，绝不编造。"""

user_question = "评标委员会至少几人？有没有奇偶数要求？"

# 【关键 2】把 system 放在 messages 第一条，永远排在最前
response = client.chat.completions.create(
    model="qwen-plus",
    messages=[
        {"role": "system", "content": system_prompt},   # 定人设
        {"role": "user", "content": user_question},     # 用户提问
    ],
    temperature=0.2,        # 【关键 3】0-2 之间：越低越稳定，事实类问答用 0.1-0.3
    max_tokens=500,         # 【关键 4】限制输出长度，避免超预算
    top_p=0.9,              # 【可选】和 temperature 二选一调；一般默认 0.9 够用
)

print("=== 回答 ===")
print(response.choices[0].message.content)
print(f"\n[usage] 输入 {response.usage.prompt_tokens} tokens, "
      f"输出 {response.usage.completion_tokens} tokens, "
      f"finish={response.choices[0].finish_reason}")
关键参数对照
temperature=0.2低温 → 稳定、少发挥。事实问答、抽取任务用
temperature=0.8-1.0高温 → 有创意、多样化。文案、脑暴用
max_tokens=500约 350 个中文字。政企场景常用 800-2000

跑一遍，再把 temperature 改成 1.2 跑一遍——同一个问题，感受下答案的"抖动幅度"。这是你对"模型稳定性"最直接的一课。

📌 案例 A · 跟做：v3 加多轮对话历史
目标

模型能"记得"上一轮说了啥——这是所有 Chatbot / Agent 的最小骨架。

完整代码 · hello_llm_v3.py
# -*- coding: utf-8 -*-
# hello_llm_v3.py —— 简易多轮对话（记忆靠维护 messages 列表）

import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

# 【核心思路】模型本身"无状态"，多轮对话靠你把历史都塞进 messages
history = [
    {"role": "system", "content": "你是招投标顾问，简洁回答。"}
]

def chat(user_input: str) -> str:
    """一次对话：把用户话拼进历史，请求，收回答，再拼进历史。"""
    history.append({"role": "user", "content": user_input})   # 记用户说的话

    try:
        response = client.chat.completions.create(
            model="qwen-plus",
            messages=history,
            temperature=0.3,
        )
        answer = response.choices[0].message.content
        history.append({"role": "assistant", "content": answer})   # 记模型说的话
        return answer
    except Exception as e:
        # 【关键】异常兜底：网络抖动、限流、超时都可能出错
        return f"[调用失败] {type(e).__name__}: {e}"

# 简单命令行循环
if __name__ == "__main__":
    print("多轮对话 Demo（输入 quit 退出）")
    while True:
        q = input("\n你: ").strip()
        if q.lower() in ("quit", "exit", "q"):
            break
        print(f"AI: {chat(q)}")
        print(f"[历史长度 {len(history)} 条]")
试试这个对话
  1. 你："某市政采购项目预算 800 万，评标委员会几人？"
  2. 你："刚才那个项目，如果我想缩短评审时间，能怎么办？"（看模型能否记住"800 万政采"这个上下文）
⚠️ 多轮对话的成本坑
每轮都会把 全部历史 一起发给模型——第 10 轮时你发过去的 prompt_tokens 已经很大。生产环境要做"历史截断/摘要压缩"，Day 8 会讲。
🧪 案例 B · 自练 1：写一个"翻译助手"（英译中，可控风格）

需求：输入英文，输出中文。支持两种风格：正式（合同、公告用）、口语（邮件、聊天用）。

动手前先想 3 件事：

  1. system_prompt 里怎么写风格约束？
  2. user 消息里除了原文还要传什么？（提示：风格参数）
  3. temperature 用多少？（翻译要稳定，别太发挥）

# translator.py
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

def translate(text: str, style: str = "formal") -> str:
    """英译中；style: formal(正式) / casual(口语)"""
    style_hint = {
        "formal": "用正式书面语，保留专业术语，适合合同/公告场景。",
        "casual": "用口语化中文，通顺自然，适合邮件/聊天场景。",
    }[style]

    response = client.chat.completions.create(
        model="qwen-plus",
        messages=[
            {"role": "system",
             "content": f"你是专业中英翻译。要求：{style_hint} 只输出译文，不加解释。"},
            {"role": "user", "content": text},
        ],
        temperature=0.2,   # 翻译要稳定
    )
    return response.choices[0].message.content

if __name__ == "__main__":
    en = "The Contractor shall deliver the equipment by December 31, 2025."
    print("正式:", translate(en, "formal"))
    print("口语:", translate(en, "casual"))

关键点：用 f-string 把风格参数拼进 system_prompt，一句话切换风格；temperature=0.2 保证同一句英文每次翻译结果基本一致。

🧪 案例 C · 自练 2：写一个"合同摘要器"（长文本→结构化摘要）

需求：输入一段 1000+ 字的合同文本，输出结构化摘要：合同标的 / 甲方 / 乙方 / 金额 / 签约日期 / 关键条款。

提示：

  1. system_prompt 里要明确列出摘要的 6 个字段；
  2. 让模型用 Markdown 表格返回（Day 5 会讲怎么强制 JSON）；
  3. max_tokens 给足（建议 800+），避免摘要被截断；
  4. 每次调用打印 finish_reason，看有没有 length。
查看参考实现 
# contract_summarizer.py
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

SYSTEM = """你是合同摘要助手。请从下方合同全文中抽取 6 个字段，用 Markdown 表格输出：
| 字段 | 内容 |
| 合同标的 | ... |
| 甲方 | ... |
| 乙方 | ... |
| 合同金额 | ... |
| 签约日期 | ... |
| 关键条款 | 逗号分隔的 3-5 条 |
未找到的字段填"未提及"，绝不编造。"""

def summarize(contract_text: str) -> dict:
    resp = client.chat.completions.create(
        model="qwen-plus",
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": contract_text},
        ],
        temperature=0.1,     # 抽取任务用最低温
        max_tokens=1000,     # 摘要留足空间
    )
    return {
        "content": resp.choices[0].message.content,
        "tokens": resp.usage.total_tokens,
        "finish": resp.choices[0].finish_reason,
    }

if __name__ == "__main__":
    contract = open("sample_contract.txt", encoding="utf-8").read()
    result = summarize(contract)
    print(result["content"])
    print(f"\n[烧了 {result['tokens']} tokens, finish={result['finish']}]")
    if result["finish"] == "length":
        print("⚠️ 警告：被截断，请调大 max_tokens")

关键点：抽取任务用 temperature=0.1 保稳；摘要器永远要检查 finish_reason；用"未找到填未提及，绝不编造"这句话大幅降低幻觉。

📇 四、速查卡

🩺 常见错误码对照表（错了不慌）
状态码含义怎么办
400 Bad Request参数不对：model 名写错 / messages 格式错 / 图片超大回头对着官方文档核参数，重点看拼写
401 UnauthorizedKey 无效：拼错、过期、被禁用回控制台重生成 Key；检查环境变量是否加载
403 Forbidden没权限：该模型你账号没开通控制台申请开通模型；或换个已开通的模型
429 Too Many Requests限流：调太快，触发 QPS 限制加 time.sleep(1) 或做指数退避重试
500 Internal Error服务端问题：模型抽风或平台故障重试 1-2 次，仍不行去平台状态页看有无告警
Timeout超时：长文本推理慢 / 网络差设置 timeout=60，或换更快的 model（qwen-turbo）
⚙️ 核心参数速查（每个都要能一句话说清）
参数作用推荐值
temperature随机性：越高越发挥，越低越稳定抽取/翻译 0.1-0.3；对话 0.5-0.7；创意 0.8-1.2
top_p核采样：只从概率累积 top_p 的 token 里选默认 0.9；和 temperature 二选一调，别同时
max_tokens限制输出长度上限短问答 300-500；摘要/生成 800-2000；文档 4000+
stop遇到指定字符串就停止生成结构化输出常用，如 stop=["\\n\\n"]
stream流式返回：一个 Token 一个 Token 推用户交互场景 True（体验好）；后台任务 False
n返回几个候选答案一般 1；A/B 测试或投票时用 3-5
timeout整体请求超时秒数默认 60；长文本设 120；关键路径永远设
🔐 让 API Key 更安全的 3 种做法
  1. 本地开发用 .env 文件——项目根目录建 .env，配 .gitignore 把它排除。python-dotenv 自动加载。
  2. 生产环境用环境变量或密钥管理服务——K8s Secret / AWS Secrets Manager / 阿里云 KMS。代码里永远 os.getenv()。
  3. Key 定期轮换 + 最小权限——每 90 天换一次；给不同应用发不同 Key；能限制额度就限制。万一泄漏，一键禁用旧 Key。

红线：永远不要把 Key 写在代码里、粘到聊天群里、截图给客户看。

📝 五、5 题小测验

先想 30 秒再点开答案。错项解析才是这一节的核心资产。

Q1 · 抽取合同关键字段的任务，你应该把 temperature 设成多少？
  • A. 1.5（要模型充分发挥）
  • B. 0.7（默认值就好）
  • C. 0.1-0.2（越低越稳定）
  • D. 完全不设，让模型自己决定
✅ 答案：C

抽取任务追求稳定、可重复、不编造——同一份合同今天抽出来的甲方和明天抽出来的必须一致。低温（0.1-0.2）让模型选概率最高的 token，输出趋近确定性。

❌ 错项解析

A 错得离谱——1.5 是创意写作用的高温，抽取任务用高温等于让模型"猜着抽"，同样一份合同两次抽的甲方可能不一样。B 是默认值——默认 0.7 适合聊天，抽取偏高，会出现"看起来合理但其实错"的答案。D 错在没主动控制——参数不设走默认值，等于放弃了对稳定性的调优。

Q2 · 调用返回 finish_reason="length"，说明什么？
  • A. 模型自然结束，一切正常
  • B. 输出被 max_tokens 上限截断了，结果可能不完整
  • C. 输入太长，请求被拒
  • D. 模型触发了安全策略
✅ 答案：B

length 意味着模型话没说完就被 max_tokens 卡断了——生产环境下这是重大 Bug。合同摘要抽到一半、JSON 结构没闭合，直接程序崩。PM 必须每次调用都检查这个字段。

❌ 错项解析

A 错在混淆了 stop 和 length——正常结束是 stop，length 是被截断，两者本质不同。C 错在错误归因——输入过长会返回 400 错误码，不是走 finish_reason 这条路。D 错在字段搞错——安全策略触发是 content_filter，不是 length。

Q3 · 你的代码 push 到 Git 后突然收到平台账单短信，最可能是啥原因？
  • A. 服务器被 DDoS 攻击
  • B. API Key 硬编码在代码里被爬取到，遭黑产刷 Token
  • C. 阿里云平台故障，账单算错
  • D. 你的代码有死循环，调用不停
✅ 答案：B

GitHub 上有专门的黑产脚本 24 小时扫 sk- 开头的字符串，一旦发现立刻用你的 Key 刷模型。这是新人最贵的一课——永远用环境变量读 Key，永远配 .gitignore 排除 .env。

❌ 错项解析

A 错在张冠李戴——DDoS 攻击不会让你的账单飙升，只会让服务响应变慢。C 是甩锅思维——平台账单极少算错，先自查自己的 Key 是否泄漏。D 可能但不是主因——死循环通常你自己能发现（进程还在跑），黑产刷 Key 是无感的更可怕。

Q4 · 一次调用 usage 显示 prompt_tokens=8000 / completion_tokens=200，说明什么？
  • A. 输入很长，输出很短——典型的抽取或摘要任务
  • B. 输入很短，输出很长——典型的生成任务
  • C. 模型抽风了，输入输出不平衡
  • D. 计费出错，应该退款
✅ 答案：A

输入 8000 Token（约 6000 中文字）、输出 200——非常典型的"读长文档、出短结论"场景，比如合同摘要、简历筛选、会议纪要抽取。PM 要建立的直觉：抽取/摘要类任务，prompt_tokens 通常是 completion_tokens 的 10-100 倍——所以要重点优化的是输入压缩，不是输出。

❌ 错项解析

B 正好反了——生成任务是输入短输出长（比如"写一份 500 字周报"），typical prompt=50 / completion=800。C 是不懂业务——不同任务类型 usage 分布本来就不同，不平衡不代表错。D 是甩锅——usage 计费是按 Token 精算的，很少出错，先看自己的任务模式。

Q5 · 综合题——你的调用返回 429，怎么处理最合适？
  • A. 立刻重试 100 次，直到成功
  • B. 加 time.sleep(0.5) 后重试，最多 3 次；仍失败则记日志报警
  • C. 换个 Key 继续调
  • D. 忽略，反正下次调用可能就成功了
✅ 答案：B

429 表示限流，说明你调太快了。正确工程做法是"指数退避重试"：第 1 次等 0.5 秒、第 2 次等 1 秒、第 3 次等 2 秒，超过 3 次记日志告警。这是生产环境的基本盘。

❌ 错项解析

A 错在暴力重试——不加间隔的重试 100 次会加剧限流，还可能触发平台风控封 Key。C 错在绕过限制——换 Key 是钻空子，一旦被平台识别可能封整个账号；正确做法是限流后退避。D 错在没有工程意识——生产系统"忽略错误"就是等着凌晨被人叫醒。

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. "调 API"根本不难——5 行 Python 就能跑通。难的是你敢不敢在客户面前说"我跑过"。（PM 转 FDE 的心理关比技术关重。）

2. Response 里最值钱的不是 content，是 usage 和 finish_reason。（这两个字段决定了成本和完整性，PM 视角比开发视角更该看。）

3. temperature 不是"随便设"——抽取用 0.1 / 对话用 0.5 / 创意用 1.0，是三档决然不同的策略。（PM 要能一眼看出场景该用哪档，这是需求判断力。）
