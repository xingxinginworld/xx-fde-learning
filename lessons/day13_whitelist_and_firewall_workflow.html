📖 二、核心讲解

是什么：白名单申请的 3 个环节

大白话——白名单就是客户防火墙上的"通行证名单"。你的服务要访问外网任何域名/端口，都得先登记、审批、放行。没登记的流量，一律掐断。

环节干什么交付物常见耗时
① 准备梳理依赖清单、估算流量、写业务合理性说明《白名单申请单》1-2 天（你自己干）
② 申请走审批链：IT → 安全 → 网络运维（有时加合规）审批通过记录3-15 天（看客户效率）
③ 落地网络运维开策略、你做连通性验证、归档清单《白名单清单 v1》1-2 天

关键认知：耗时大头在环节 ②，而环节 ② 快不快的决定因素，是环节 ① 你准备得专不专业。申请单越专业，审批链越短。

□ □ □ 申请单 5 要素口诀 □ □ □
域 · 端 · 量 · 期 · 批
域名清单 / 端口清单 / 流量峰值估算 / 有效期 / 审批归属人 · 缺一必被退回

为什么：3 个高频翻车点

🚨 坑 1 · 只申请 API 域名，不申请依赖域名

你申请了 dashscope.aliyuncs.com，批了。结果部署当天 pip install 装不上依赖——因为你没申请 pypi.org 和 files.pythonhosted.org。模型要下载？huggingface.co 也没开。SDK 要上报心跳？又被掐。

正确姿势：申请前把"开发期 / 推理期 / 部署期"三个阶段的出网需求一次性列全（见速查卡 2）。

🚨 坑 2 · 端口只申请 443

你以为 HTTPS 就完事了。结果流式输出要走 WebSocket（部分服务用 8443 等非标准端口）、私有化镜像仓库走 5000、数据库走 3306/5432——每一个没申请的端口都是一次现场翻车。

正确姿势：画一张"服务间调用图"，把每一跳的端口都标出来，一次申请全。

🚨 坑 3 · 忘记回程流量估算

安全部最关心两件事：数据往哪走、流量有多大。你申请单上写"日常调用"，安全部直接退回——"峰值 QPS 多少？单日流量多少 GB？写清楚再来"。一来一回 3 天没了。

正确姿势：用 Day 3 学的成本估算方法，把 QPS 峰值 + 单日 token 量 + 折算流量 算出来写进申请单。数字越具体，审批越快。

🧭 PM 行动指南：白名单申请前必备 4 件东西

① 域名清单：主域名 + 依赖域名，逐个注明用途。

② 端口清单：每个域名对应的端口和协议（HTTPS/WSS/TCP）。

③ 流量峰值估算：QPS 峰值、单日调用量、折算出口流量。

④ 业务合理性说明：一句话说清"不开这条，哪个业务功能就瘫痪"。

怎么用：白名单申请全流程 5 步

1
梳理依赖清单——按"开发期 / 推理期 / 部署期"三阶段列出所有出网域名和端口。别只盯着主 API。
2
写申请单——5 要素（域·端·量·期·批）齐全，附业务合理性说明。用速查卡 1 的模板，填空即可。
3
走审批链——一般是 IT（归属确认）→ 安全（数据合规审查）→ 网络运维（开策略）。提前约好三方时间，别串行干等。
4
验证连通——nslookup 域名 看 DNS 解析 → telnet 域名 端口 看端口通不通 → curl -v https://域名 看握手和证书。三步全绿才算通。
5
归档白名单清单——把批准的域名/端口/有效期/审批单号存成《白名单清单 v1》交给客户运维。到期前 30 天提醒续期。

🛠️ 三、动手步骤：走一遍真实申请流程

导师说

下面三个案例，第一个我带你完整走一遍，连申请单原文都给你。后两个是你进场一定会遇到的场景，自己练。

📌 案例 A · 申请阿里云百炼 API 上内网（跟着做）
Step 1 · 依赖清单（三阶段）
推理期dashscope.aliyuncs.com:443（模型推理主入口）
开发期bailian.console.aliyun.com:443（控制台查用量/管 Key）
部署期pypi.org:443 + files.pythonhosted.org:443（装依赖，若走离线包则不用）
Step 2 · 申请单原文（模板填空版）
申请事由：智能员工问答系统需调用大模型推理服务。
域名清单：
  1. dashscope.aliyuncs.com  端口 443  HTTPS  用途：模型推理
  2. bailian.console.aliyun.com  端口 443  HTTPS  用途：用量监控
端口：443（HTTPS）
流量估算：峰值 20 QPS，单日约 5 万次调用，
  出口流量约 2 GB/天（单次请求+响应约 40KB）
有效期：12 个月（到期前 30 天续期）
归属人：XXX（项目组）  业务对接人：XXX（信息部）
业务必要性：若该域名不可达，员工问答功能整体不可用。
Step 3 · 审批链上的 3 种典型对手 & 应对
网络运维问："峰值 20 QPS 怎么来的？"答：日活 800 人 × 人均 8 次 ÷ 8 小时 ÷ 3600 秒 × 峰均比 3 倍，附计算过程
安全部问："数据出不出境？"答：阿里云国内节点，附服务商合规说明 + 数据不落境外承诺
IT 部问："出了事谁负责？"答：归属人写项目组负责人，附应急预案一页纸
Step 4-5 · 验证 + 归档

nslookup dashscope.aliyuncs.com → 有解析；telnet dashscope.aliyuncs.com 443 → Connected；curl -v https://dashscope.aliyuncs.com → 200。三步全绿，归档清单，收工。

🧪 案例 B · 申请 Hugging Face 模型下载白名单（自己练）

场景：你要在客户内网部署一个开源模型，需要从 huggingface.co 下载权重文件（约 40GB）。你按案例 A 的格式提交了申请。

问题：在政企客户处，这个申请大概率被拒。先自己想 3 个被拒理由，再想 2 个替代方案。

查看参考答案

常见被拒理由：① 境外站点，安全部对"境外大流量下载"天然警惕；② 40GB 单次下载流量远超日常基线，触发风控；③ 模型来源不可控，安全部担心夹带风险。

替代方案（按推荐顺序）：① 改用国内镜像源（如 hf-mirror.com 或 ModelScope），域名境内、合规好讲；② 在你自己办公室下载好，走客户"介质导入流程"（U 盘/光盘 + 杀毒 + 审批）拷入内网——政企对"介质导入"有成熟流程，比开境外白名单容易 10 倍。

核心认知：白名单不是唯一通路。流程上走得通的路，才是好路。

🧪 案例 C · 申请被拒：「跨境数据传输风险」申诉（自己练）

场景：你的白名单申请被安全部驳回，理由一行字："涉及跨境数据传输风险，不予批准。"但你知道你用的明明是国内云服务商。

写一份 3 层申诉方案。提示：先证明、再补材料、最后给替代。

查看参考答案

第 1 层 · 证明数据不出境：附服务商的《数据中心位置说明》（国内节点）+ 服务协议中"数据境内存储"条款截图 + 一次 traceroute 结果证明链路不出境。

第 2 层 · 补合规材料：主动提交《数据流向图》（Day 16 会细讲）+ 承诺"提示词与业务数据不用于服务商模型训练"的条款引用。

第 3 层 · 给替代方案："若仍不批准公有云方案，我方提供私有化部署备选（Day 14 选型），请安全部评估两条路径哪条更符合合规要求。"——把"对抗"变成"选择题"，审批通过率大增。

话术金句："我不是来求您放行的，我是来帮您把合规证据链补全的。"

📝 五、5 题小测验

先自己想 20 秒再点开答案。错项解析比正确答案更值钱。

Q1 · 白名单批下来就永久有效，对吗？
  • A. 对，批一次管到项目结束
  • B. 不对，一般有有效期，到期要续期，且人员/架构变动可能触发重新审批
  • C. 对，但每年要交一次费用
  • D. 不对，白名单每天随机抽查
✅ 答案：B

白名单通常有有效期（常见 6-12 个月），且客户安全策略调整、项目归属人变更都可能触发复核。所以 Step 5 才强调"归档 + 到期前 30 天提醒续期"。项目上线半年后突然 API 不通，十有八九是白名单到期没人续。

❌ 错项解析

A 错在把审批当一锤子买卖——政企安全策略是动态的。C 错在编造费用——白名单是安全策略不是收费服务。D 错在臆想机制——没有"每天抽查"这种机制，但有到期失效和策略调整。

Q2 · 部署当天发现 pip install 全部超时，最可能的原因是？
  • A. 客户机器性能太差
  • B. 申请白名单时只申请了推理域名，没申请 pypi 依赖域名
  • C. pip 版本太旧
  • D. 依赖包本身有 bug
✅ 答案：B

这是坑 1 的原现场景。推理域名通了不代表依赖域名通了。预防方法：申请前按"开发期/推理期/部署期"三阶段列全清单；或者干脆走离线 wheels 包（Day 15），彻底不依赖外网。

❌ 错项解析

A/C/D 都是"技术归因"，在政企内网环境里，"网络不通"永远要排在"技术故障"前面排查。记住判断顺序：先问通不通，再问对不对。

Q3 · 申请单 5 要素「域·端·量·期·批」中，「批」指的是？
  • A. 批量申请的折扣
  • B. 审批归属人（谁负责、出了事找谁）
  • C. 批评与自我批评
  • D. 批处理任务
✅ 答案：B

「批」= 审批归属人。政企流程里"责任到人"是审批能推进的前提——没有归属人的申请单，三个部门谁都不敢批。写清归属人+部门+电话，是申请单能被受理的第一条件。

❌ 错项解析

A/D 是技术/商务臆想，与安全审批无关。C 是凑数选项。这题考的是你对政企"责任文化"的理解：流程的本质是责任分配。

Q4 · 连通性验证的正确顺序是？
  • A. curl -v → telnet → nslookup
  • B. nslookup（DNS 解析）→ telnet（端口连通）→ curl -v（握手+证书）
  • C. telnet → curl -v → nslookup
  • D. 直接跑业务代码看报不报错
✅ 答案：B

从底层到上层逐层验证：DNS 解析得了吗？→ 端口通吗？→ HTTPS 握手和证书正常吗？三层全绿才轮到业务层。哪层红了，问题就定位在哪层——DNS 红找网络运维查解析，端口红查防火墙策略，证书红查中间盒是否做了 SSL 劫持。

❌ 错项解析

A/C 顺序颠倒——上层通了不代表下层没问题，且颠倒后无法分层定位。D 是最差的排查方式——业务报错信息往往模糊（"connection error"），无法告诉你死在哪一层。

Q5 · 综合题——安全部以「数据出境风险」驳回你的公有云 API 申请，但你用的是境内服务商。请给出处理思路。

用案例 C 的三层申诉框架作答。

✅ 参考答案

第 1 层 证明：服务商数据中心境内位置说明 + traceroute 链路证明 + 服务协议"数据境内存储"条款。

第 2 层 补材料：提交《数据流向图》+ "业务数据不用于模型训练"条款引用，把安全部的担心逐项写成证据链。

第 3 层 给替代：同时提交私有化部署备选方案，请安全部在两条路径中选更合规的——把对抗变成选择题。

底层心态：安全部不是敌人，是帮你把合规证据链补全的同事。你的目标是让他"敢批"，不是让他"认输"。

💼 六、面试金句预埋

流程意识 "政企 AI 项目里，白名单申请是技术工作，不是行政工作。依赖清单、端口清单、流量估算、合规证据链——你准备得越像工程师，审批链就越短。"
排查顺序 "在客户内网排查问题，我永远先问'通不通'，再问'对不对'。DNS、端口、证书三层验证全绿之前，不看业务代码。"
协作心态 "安全部驳回不是刁难，是他在履职。我的做法不是申诉到底，而是帮他把合规证据链补全，或者给他一个更合规的替代方案——把对抗变成选择题。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. 卡住项目的往往不是技术，是一张申请单。（85% 的政企 AI 项目在白名单环节耗掉 2-3 周。）

2. 白名单不是唯一通路。（介质导入、离线包、国内镜像、私有化——流程上走得通的路才是好路。）

3. 申请单的专业度决定审批链长度。（你写得越像外行，被问的轮次就越多；数字越具体，批得越快。）
