## 案例 1：Jina Rerank 境外服务连接超时（已解决，实测复现）

**现象**：首次全量跑评测时，首题总耗时 **24.4s**（正常应 3s 左右），控制台打出
`⚠️ 重排失败，回退向量粗排：ConnectTimeoutError api.jina.ai (connect timeout=30)`，后续题目恢复正常。

**定位**：
- 计时剖析显示慢的是 **rerank 段**，不是检索段（0.7s）也不是生成段（2s）；
- `model_client._rerank_jina` 用 `requests.post(..., timeout=30)` 调 `api.jina.ai:443`，沙箱/评审网络到境外域名连接超时；
- `retriever.retrieve()` 捕获异常后走 L4 兜底：按向量相似度降序取 Top-5。

**归因**：
- 直接原因：评审环境无境外网络，Jina（境外 SaaS）不可达；
- 根因：**架构上把「精排质量」押在了一个境外可选依赖上**，没有把它设计成可一键旁路的组件。这正是政企适配要抓的点。

**已做改进（已验证）**：
1. 兜底链路本就生效——超时后自动回退向量粗排，答案无回退（实测：降级后 13 题评测仍 13/13 全过，检索命中率 100%）；
2. 增加 `RERANK_PROVIDER=none` 开关，显式禁用 rerank，**单题总耗时从 24.4s 降到 2.8s**（省去 30s 超时等待）；
3. 文档（02 架构适配）明确：政企环境禁用 Jina，替换路径 = none 降级 / 内网 bge-reranker / dashscope。

**遗留**：纯向量粗排在段落数极大（万级块）时排序精度会下降，私有化部署时应恢复内网 reranker。

## 案例 2：标书未提及的问题——生成端差点「好心编造」（设计期拦截）

**现象**：测试题「智能评标系统项目的项目经理需要持有什么资格证书？」，三份标书**均未提及**项目经理证书要求。若直接走生成，Qwen3-8B 有较强动机「补全」一个看起来合理的答案（如「PMP 或软考高项」）——这是 RAG 系统最危险的幻觉形态：**基于领域常识而非原文**。

**定位**：
- 该题向量相似度最高块仅 0.37 < 阈值 0.4（恰好卡在阈值下），粗筛候选不足 → `retriever` 返回空；
- 但即使过了阈值、召回到「资质要求」相关块（语义相近但**内容不含证书要求**），生成端仍可能编造。

**归因**：
- 检索端只能保证「找到相关块」，**不能保证「块里真有答案」**；
- 编造风险在生成端，靠模型自觉不可靠，必须用系统提示词硬约束 + 输出校验双保险。

**已做改进（已验证，eval_result.json 第 13 题）**：
1. `generator.SYSTEM_PROMPT` 写入硬规矩：「只用参考资料里的信息」「参考资料没写的，直接说『文档中未提及』」「金额/日期/责任主体必须一字不改引用原文」；
2. 实测结果：回答「**文档中未提及**」，`confidence: low`，`citations: []`（不附引用，避免假溯源）；
3. 检索层再加一道：相似度 0.4 阈值过滤把低相关块挡在生成 prompt 外（本案 0.37 被挡）。

**待做**：对「答案关键词与召回块零重叠」的 case 加后置校验（命中则强制降置信为 low 并提示人工复核）——本次 3 份标书规模下未触发，规模放大后需要。

## 案例 3：引用来源页码渲染错乱「第第1页页」（已修复，真实运行发现）

**现象**：评审前复跑 CLI 时，引用来源显示
`[1] tender_zb2026_001.pdf 第第1页页`——页码前后缀重复拼接，观感是系统「坏了」。

**定位**：
- `chunks.json` 里部分块的 `page` 元数据是字符串 `"第1页"`（带中文前后缀），部分是数字 `1`（build_index 不同分支产出格式不一致）；
- `ask.py` 统一按 `f"第{page}页"` 拼接 → 数字变「第1页」（对），字符串变「第第1页页」（错）。

**归因**：
- **数据元数据 schema 不统一**：同一字段两种格式，消费端做了单一假设。这是「小模型 + 人工标注/抽取混合」数据源最常见的坑。

**已做改进（已验证）**：
```python
pg = str(c.get("page", "?"))
page = pg if pg.startswith("第") else f"第{pg}页"   # 兼容两种格式
```
修复后显示 `[1] tender_zb2026_001.pdf 第1页`。

**沉淀**：`build_index.py` 应在写入 chunks.json 时**归一化 page 字段为纯数字**（治本），本次为控制改动面只在消费端做了兼容（治标），私有化正式版会补归一化。

## 案例 4：跨文档汇总题——Top-5 段落不够「数数」用（观测到，低风险）

**现象**：题 12「请列出本次所有招标项目的名称和招标编号」需要覆盖 **3 份文档**的关键信息。`TOP_K=5` 下实测能答对（三项目全列出），但召回的 5 段中有 2 段来自同一文档的次要内容（资质/服务期段落），信息密度被稀释——答对靠的是模型在 3 份文档第 1 页块上都命中了编号，属于**运气偏好的正确**。

**定位**：
- 粗筛 COARSE_K=20 → 阈值过滤后候选 8 块 → rerank Top-5；
- 「列举全部」类问题与「单点事实」类问题对召回策略需求不同：前者需要**跨源多样性**，后者需要**单源精度**。

**归因**：单一 Top-K 策略对问题类型无感知，没有做 per-query 的召回策略切换。

**改进（列入待办，本次不阻塞）**：
1. 检测「列出/所有/全部/汇总」类问法 → 自动把 TOP_K 提到 8~10；
2. 或对候选按 source 做轮转采样（round-robin），保证 Top-K 尽量跨源；
3. 在 `eval_demo.py` 基线里保留该题，改动后回归。
